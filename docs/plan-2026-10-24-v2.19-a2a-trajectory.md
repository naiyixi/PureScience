## 1. A2A 映射到现有 ACP 会话

A2A（agent-to-agent）的核心对象是 **Agent Card**（能力声明）与 **Task**（可轮询的状态机：submitted →
working → input-required → completed/failed/canceled，产物以 Artifact 形式回传）。本产品内部的一切对话
已经跑在 ACP 会话上（`src/main/acp/*`：会话注册表、能力所有者、provider 会话创建器）。

映射原则：**A2A 是外壳，ACP 会话是执行体；不新造第二套会话模型。**

| A2A                         | 映射到                                    | 说明                                                                                                                                                                      |
| --------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/agent-card`               | 由现有能力契约生成                        | `SessionCapabilityDescriptor`（role/capabilities/canonicalMcpServerNames）已经是最接近的事实来源；Agent Card 的 `skills` 段取技能注册表里**已物化**的条目，不额外造元数据 |
| `message/send`（新建 Task） | `createSession` + 第一次 prompt           | 复用现有会话建立（含 MCP 就绪预算与重试）；Task id 与 appSessionId 一一对应并存                                                                                           |
| `tasks/get`（轮询）         | 会话状态 + 最近一轮事件                   | 只读投影，不额外写盘                                                                                                                                                      |
| `tasks/cancel`              | 现有 stop/cancel 通道                     | 与窗口上的「停止」同一路径，避免两套取消语义                                                                                                                              |
| Task Artifact               | 现有 artifact 版本（`artifactVersionId`） | 不复制字节，只暴露定位符与校验和                                                                                                                                          |
| `input-required`            | 现有权限/计划审批闸门                     | 这正是本产品「权限门」的强项：A2A 的等待态直接映射到审批，而不是让调用方猜测                                                                                              |

**必须保持的不变量**：会话仍是唯一权威（durable JSON + SQLite 投影）；A2A 层不拥有状态，重启后由权威
重建；任何 A2A 写操作都走既有 `withSessionMutation`/队列，不绕过。

## 2. 轨迹包（trajectory bundle）包含什么

一个轨迹包 = 一次（或一串）会话的可复现证据，目录形态（zip 或 tar）：

```
trajectory/
  manifest.json         # bundle 版本、生成时间、产品版本、会话 id、轮数、哈希清单
  session.json          # 权威会话文档的**脱敏副本**（结构不变，凭证 REDACTED）
  events.jsonl          # 每轮的事件流（prompt/工具调用/usage/审批/停止原因），按时间序
  tool-calls.jsonl      # 工具名、参数摘要、耗时、结果大小与哈希（结果正文可选，默认不含）
  artifacts.json        # artifactVersionId / 校验和 / 生成该版本的 run id（不含字节）
  capabilities.json     # 该会话实际挂载的 MCP 服务清单与分组（来自 v2.17.5 的 servers/groups 读数）
  checksums.sha256      # 上述每个文件的 sha256
```

**脱敏规则（硬性）**：

- 凭证一律 `REDACTED`：provider api key、`keyRef`/`keyMask` 原文、cookie、Authorization 头、连接器密钥、
  `safeStorage` 密文、钥匙串条目名之外的一切秘密材料。
- 路径只保留「位置类别」（默认/自定义），不保留用户名与目录名（沿用现有 `data root resolved` 的做法）。
- 提示词与工具结果属于用户内容：默认包含，但提供 `--no-content` 只出结构+哈希的模式。
- **做不到就不打**：任何字段如果只能靠猜，宁可不写进包，也不写一个看起来像证据的占位符。

## 3. 复现需要什么

- 消费端需要：同版本产品、同模型 id、同 MCP 服务清单（`capabilities.json` 可核对）、同工具版本；
  差异要显式报告而不是静默降级。
- 复现不是「重放字节」，而是「同一输入 + 同能力 → 可比对的事件序列」：因此包内必须含每轮的输入快照与
  所用模型/框架/runtime 版本。
- 至少一条端到端验证：把包交给另一台机器上的同版本实例，能打开会话、能读到同样的工具序列与 usage 行。

## 4. 明确没做（本设计阶段）

- 没有 A2A 服务器、没有 agent card 端点、没有轨迹包导出实现；
- 没有与外部 A2A 实现做过互通测试（任何「兼容 A2A」的说法在实测之前都不成立）；
- 脱敏清单是设计承诺，尚未有自动化用例证明「包里没有凭证」。

### 7.1 `capabilities` 投影：三层锚点（本轮勘察结论，代码未动）

这不是加一个字段，而是把「会话建立时到底挂了哪些服务」从 runtime 一路带到持久化层，共三层：

1. **持久化**（`src/shared/session-persistence.ts`）：`PersistedChatSession` 加 `sessionCapabilities?:
{ servers: string[]; groups?: string }`；照 `contextUsage` 的形状写 sanitize（类型定义 ~L359、
   sanitize 调用点 ~L1745、`sanitizeAcpContextUsage` 是模板）；规则：非空字符串、去重、条数与长度上限、
   **缺席即「未记录」而不是「没有能力」**。
2. **descriptor 在谁手里**：`src/main/acp/provider-session-creator.ts:114-121`（
   `capability.descriptor.capabilities` 与 `canonicalMcpServerNames`）—— 这里是唯一知道真相的地方。
3. **durable 文档在谁手里写**：`src/main/ipc.ts:923` 与 `1710`（`sessionPersistenceCoordinator.saveSession`）
   以及 `src/main/tasks/task-runner.ts:479,494`（写 `agentFrameworkId` 的那处）。**这两处与第 2 步不在同一层**
   —— 这就是为什么它不是「一个字段」的改动：要么让 runtime 把 descriptor 传上去，要么在保存时回查。

**已落地**（同一轮完成，五处小改）：`PersistedChatSession.sessionCapabilities?` +
`sanitizeSessionCapabilityProjection`（只收非空字符串、去重、条数与长度上限、**缺席 ≠ 没有**）；
`AcpCreateSessionResponse.capabilities?`；`provider-session-creator` 在提交权限后捕获
`descriptor.canonicalMcpServerNames`；`task-runner` 在建文档时写入；`ipc.ts` 的 facts 读它。
用例：5 例持久化（含「未记录」与「没有」分开、去重、形状非法）+ 原有轨迹用例。
`manifest.sections.capabilities` 从此在真机上新会话里会读到 `included`。

## 5bis. 附：接线成本核算（同日，结论已并入 §6/§7）

**不要新造一套脱敏表。** 仓里已有 `src/main/diagnostics/support-bundle.ts`，它做的正是这件事：
`scrubText()` 按 `SECRET_PATTERNS` + 家的路径/用户名做替换，`findLeak()` 在**归档回读之后**再查一遍，
一旦命中就删包并抛错（「宁可失败，也不交出泄漏」）。轨迹包应当**复用**这个 `scrubText`/`findLeak`
（导出成可复用的名字），只在它上面加 §2 的字段与 `trajectory/` 目录，而不是第二套词汇表。

**真正的卡点是「谁调用它」**（本仓不接受「已建但生产无人调用」）：

- 现有入口 `support-bundle-ipc.ts` 的 `getFacts()` 拿不到会话 id —— `exportBundle(sender)` 没有参数，
  要带会话就得改共享契约 `shared/diagnostics`。
- **方案 A（新 IPC 通道）**：`diagnostics:export-trajectory` + `{ sessionId, noContent }`。牵动 8 处
  （契约目录、`gen:web-api-map` 生成物、preload + d.ts、应用命令定义/组内登记/owner `Pick`、三处命令计数、
  其余计数钉），另加渲染层入口。**连锁最大**。
- **方案 B（CLI 子命令 + 一条只读 web 路由）**：`purescience trajectory export --session <id> --out <dir>`。
  CLI 已有 `session status` / `artifacts list` 这类走 `/api/v1` 的只读命令，加一条路由 + 一个子命令即可，
  **不动渲染层、不动命令计数**。连锁最小 ⇒ 默认走这条。

**验收（§4 缺的那条）**：一条用例，在会话文档里**故意种满**各种形状的凭证（provider `keyRef`/`keyMask`、
header 里的 `Authorization`、`sk-` 前缀的假 key、`enc:`/`plain:` 密文、cookie），断言：

1. 打包后 `trajectory/session.json` 里这些值**一个都不在**（结构仍在，键在、值为 `REDACTED`）；
2. 走 `scrub:false` 的旁路时，`findLeak` 仍然**拒发**（证明检查读的是真产物，不是相信清洗）；
3. `checksums.sha256` 与包内各文件字节一致；
4. `includeContent: false` 时：消息正文不在，但轮数/工具名/哈希仍在。

这四条就是 §4 里「脱敏清单还没有用例证明」的收口。
