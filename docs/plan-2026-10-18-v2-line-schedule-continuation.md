# v2 线排期补档（v2.6.0 起）与欠账清点

日期：2026-10-18
上一份排期：`docs/plan-2026-10-10-v2-line-schedule.md`（只排到 v2.5.0）

## 〇、这份文档为什么存在

`plan-2026-10-10-v2-line-schedule.md` 的版本序列表止于 **v2.5.0**。v2.6.0 之后没有任何排期文件，
而被当作 v2.6.0 施工图引用的 `plan-2026-10-17-knowledge-tool-surface.md` **从未存在于仓库**。

后果是实际发生过的：v2.7.0–v2.10.0 这四版，是实施者在「继续做下一版」这句话下**自行选定的**——每次都
从上一版 CHANGELOG 的「明确没做」里挑一条。它们有实测、有证据、也都发了版，但**没有一条来自排期**。
这份文档把这件事追认在案，并补齐 v2.11 起该按什么顺序做。

**纪律（写在这里是为了下次不必再解释）**：任何一版动工前，先在本文档登记「版本号 / 主题 / 出生地 / 判据」；
一句话「继续」只表示「继续按本文档的下一条」，不表示「自行定义下一版」。

## 二、排期内唯一真正的缺口：H 批（设计侧引擎族）

`plan-2026-10-10-v2-line-schedule.md` 把 **v2.5.0** 定为「设计侧引擎族（H 批）：反向折叠 / binder 生成 / MD」。
实际发布的 v2.5.0 是「本地解析模型入版」，H 批**从未落地**：

| H 批条目 | 现状 | 核验方式 |
| --- | --- | --- |
| 反向折叠（ProteinMPNN 类） | 未做 | `src/shared/engine-catalog.ts` 无此项；全仓 grep 零命中 |
| binder 生成（RFdiffusion / BindCraft 类） | 未做 | 同上 |
| MD（GROMACS） | 未做 | 同上 |
| 既有引擎 | 已有：alphafold-db / pdb / esmfold / colabfold / ddg-cpu-predictor / openmm-fep / rosetta-ddg | 同文件 |

H 批不是「做了一半」：三条一条都没开工。它挂进的是既有的 engine-catalog 机制（权重许可事实 + 审批前脚本 +
一份栈一个命名环境），那套机制已经在 v2.1–v2.5 里验证过，所以开工成本主要在**引擎本身的获取与许可**。

## 四、非版本欠账（取证/评估类，来自 `handoff-2026-10-12-next-session.md`）

这四条不是功能，是「读数还没取到」，各自带解封条件；不计入版本排期：

| 项 | 解封条件 |
| --- | --- |
| 打包版界面截图 / 打包版库的 WAL 读数 | 只缺一次发版产物（v2.10.0 已发布，可解封） |
| 慢解析出现率的前后对照 | 只缺一段真实使用的时段（分母不足） |
| 只读连接（读池第二步） | 需要上一项的读数；且本机 8 GB，先量内存再谈 |
| `via` 进入持久溯源 | 需要给 env 记录加来源字段（schema 演化 + 迁移口径） |

## 五、v2.11 起的建议顺序

按「排期缺口优先于自选尾巴」排：

1. ~~**v2.11.0 — H 批第一件：反向折叠**（ProteinMPNN 类）~~ ✅ **已交付并发布（`051eaccb`）**
   判据全部拿到：许可事实入 catalog（MIT，权重实测 6,681,301 字节）、跑通真序列（1CRN 46 残基 0.29 s）、
   可复算（同 seed 两次 FASTA 逐字节相同 `1efcf49e2fa01344…`）。不做第二台引擎的一致性判据，理由见 U4-e。
2. **v2.12.0 — 清扫可观察 + 知识库面板补齐**（「上次清扫」读数 + 批量移除 + 分页）
   手动触发清扫已由远端单独交付（`f551cd2b`），本版只剩这三件。
   判据：面板上能读到上次清扫的时间与清理数；批量移除一条链有真机读数；列表超过一屏能翻页。
3. **H 批第二件：binder 生成 —— 立案，阻塞（不是排在 v2.13）**
   `blocked-by`：**一台 NVIDIA CUDA 主机**。2026-10-18 实测三条证据：
   - 官方环境 `env/SE3nv.yml` 钉 `pytorch=1.9` + `cudatoolkit=11.1` + `dgl-cuda11.1`，本机 ARM Mac 无 CUDA；
   - README 唯一的运行方式是 `docker run --gpus all`，没有 CPU 用法；
   - `SE3Transformer` 源码里 `rel_pos.cuda()` 硬编码，无 `device='cpu'` 分支。
   权重本身可达（`files.ipd.uw.edu`，241,684,523 字节，HTTP 200），所以「取不到权重」不是阻塞原因——
   **阻塞的是算力**。产品里已有 remote 引擎与 compute host 概念，这条的正确接法是 `placement: 'remote'`，
   在没有 GPU 主机可注册之前不接，也不做只能声明不能跑的条目。解封条件：能注册一台带 CUDA 的计算主机。
4. **MD（GROMACS）** —— 与 binder 相反，它从 conda-forge 取、CPU 可跑（1CRN 级体系），可作为 v2.13.0 的候选。
   判据同反向折叠：一条真轨迹 + 可复算输入指纹。
5. 排期外候选（未排，仅登记想法）：副本按内容而非文件名校验、知识库面板排序筛选、URL 来源的验证频率策略。
