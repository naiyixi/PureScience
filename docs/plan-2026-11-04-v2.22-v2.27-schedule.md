### v2.23.0 性能预算与流畅度（11-06 → 11-10）

      改成最新引用桥后 **3.7 次/回合**（160 回合 3.8 次 —— 长度 4 倍不涨），LayoutCount 15→11、
      RecalcStyleCount 27→20，行渲染总数不变（120 / 480）。同批次 40→160 回合 task **+10%**（改前 +104%）。
      证据 `docs/evidence/2026-11-05-perf-baseline-scroll-vs-streaming.md` §二十一。
- [ ] 四项预算达标（滚动 p50、长任务、弹窗开启、首屏可交互）。**2026-11-05 首份基线**（仪器自证 usable，
      真窗口）：每回合主线程 **63.9 ms** 越 50 ms 预算（10 回合共 639 ms，scripts 412 ms）——这是「卡」的实际
      来源；滚动 p95 34 ms 但**只有 39 帧**，证据不足、不作结论；IPC p50 0 ms、命令面板 46 ms、重开重会话

      63.9 ms 拆成分项再改，滚动样本做到 ≥200 帧再读。**同日补测（PERF_TURNS=40）**：每回合 task 63.9 →
      **94.2 ms**、script 41.2 → 62.3 ms、重开重会话 61 → 97 ms ⇒ 成本**随记录长度增长**，长会话才是「卡」的
      位置；CDP 采样剖析（`e2e/perf/profile-turns.spec.ts`）显示**无单点热点**（最大单项 13.4 ms/10 回合），
      工作是散的，形态是「每回合把整条记录再提交一遍」⇒ 修法应是让已沉淀回合不再参与提交（记忆化 props 或
      列表虚拟化，先量再选），不是找热点函数。**同日补测（滚动样本）**：滚动场景加长到 227/241 帧后
      **p50 = 17 ms、p95 = 33 ms、0 个超 50 ms 任务，两次复现一致** ⇒ **滚动一项可判为达标**（同 §九）；

      或把基线搬到专用 runner；在此之前只报同批次相对差与确定性计数，不报「已达标」。
      **2026-11-07 补一条口径更正**：上面这些「每回合 63.9 / 94.2 ms」全部量在**单句回复**（body 占 7%）的语料上，
