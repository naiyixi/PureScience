# U2b：`listFiles` 的代价是**两次 Prisma 往返**（7 行也一样），不是索引、不是客户端、不是闸门

- 日期：2026-09-18
- 实例：`electron-vite dev` 带窗口，独立端口 44105 / 独立 profile / CDP 9336；语料＝真实数据根副本（59 会话 / 50 项目 / 产物树硬链）
- 起点：`project-files:list-files` 被**每项目一次**调用（`HomePage.tsx:245` 取文件类型 chip），单次 95–211 ms，启动期 51 次。

## 一、段级实测（本次运行，51 次慢读全部记录）

| 段 | 中位 | 合计 | 占比 |
|---|---|---|---|
| `getClient()`（客户端获取） | **0 ms** | 0 ms | **0%** |
| 页查询 `findMany` + `count` | **47 ms** | 2,385 ms | **59%** |
| 来源查询 `fileOriginSession.findMany` | **29 ms** | 1,648 ms | **41%** |
| 行映射 `toProjectFileItem` | **0 ms** | 1 ms | **0%** |
| **合计** | **77 ms** | **4,034 ms** | 100% |

**同一份数据里每页行数中位只有 7 行（最大 30）** —— 7 行的查询要 47 ms、7 行的来源查询要 29 ms，这**不是数据量问题，是每次查询的固定开销**（Prisma 引擎往返 + 反序列化）。

## 二、四条被我依次证伪的解释（全部留档，避免重走）

| # | 解释（都很有说服力） | 判据 | 结果 |
|---|---|---|---|
| 1 | **缺索引** ⇒ 每项目一次全表扫 + 排序 | `EXPLAIN QUERY PLAN` + sqlite3 直跑真实表 | **否**：索引 `ManagedFile_projectId_deletedAt_sortAtMs_seq_idx` 存在，计划是 `SEARCH … USING INDEX`，直跑 **0–20 ms**（全表仅 463 行） |
| 2 | **恢复闸门**（每次读都 `recoverPendingDeletions`） | 段拆分仪器 | **否**：中位 **0 ms**（51 次合计 3 ms） |
| 3 | **每次调用重建客户端 / 重跑 schema** | 段拆分仪器 + `disconnectProjectDbClient` 调用点 | **否**：`clientMs` 中位 **0 ms**；仅在迁移服务里断开 |
| 4 | **并发排队**（50 个调用抢一个连接） | 日志顺序 + 时长离散度 | **否**：日志里 51 次**逐条顺序出现**，时长离散 ≤1 ms 而非"同时解锁" |

## 三、结论（下一步的靶子）

每次 `listFiles` ≈ **两次引擎往返（页查询 + 来源查询）**，与行数几乎无关。乘以**每项目一次**的扇出 ⇒ 本机启动期 **51 次 ≈ 4.0 s**（上一次负载更重的一趟是 10.8 s）。所以优化方向不在 SQL，而在**减少往返次数**：

1. **合并两次往返为一次**：来源信息并进页查询（关系 `include` 或一条 join），每调用省 ~29 ms（41%）。
2. **合并扇出**：50 个项目各调一次 → 一次批量（或只取"有哪些文件类型"的聚合，因为 Home 只渲染 chip）。
3. 先量**单次往返的地板值**（一条平凡查询的耗时），才能说清 47 ms 里有多少是引擎往返、多少是查询本身。

## 四、诚实边界

1. dev 构建；本次运行整体比上一趟轻（中位 77 ms vs 上一次 211 ms），**比例**才是结论，绝对值随负载变。
2. 单次运行、单语料（59 会话 / 50 项目 / ManagedFile 463 行）。
3. 阈值 50 ms，只记录慢读；"51 次"不等于全部调用次数。
4. **未做任何优化**：本单元交付的是段级判据与四条被证伪的解释。
