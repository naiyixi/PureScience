# U10：慢窗内 1 KB 金丝雀读 **0–1 ms**、在途 fs 操作 **1–2** ⇒ 排队假说**否**

- 日期：2026-09-18 / 实例：dev 带窗口 44105 + CDP 9336（真实语料副本）
- 仪器（已随提交落地）：`diagnostics/fs-queue-probe.ts` —— ① 在途 fs 操作计数（`beginFsOperation`/`endFsOperation`）；② **金丝雀读**：与 acquire **同时启动**、在其后 `await` 的 1 KB 文件读取（`startCanaryRead`），因此读数覆盖**同一个窗口**（事后探针做不到这一点）。

## 一、实测（本轮 3 次慢 acquire）

| # | resolveMs | statMs | **canaryMs** | **inFlightFs** | 事件循环 max |
|---|---|---|---|---|---|
| 1 | 99 | 1 | **0** | **2** | 0 |
| 2 | 100 | 0 | **1** | **1** | 0 |
| 3 | ~100 | 0–1 | **0–1** | 1–2 | 0 |

## 二、结论

1. **金丝雀 0–1 ms**（1 KB、与 acquire 同窗、页缓存热）⇒ **文件系统池没有饱和**。
2. **在途 fs 操作 1–2** ⇒ **没有队列深度**。
3. 事件循环 0 ⇒ 没有阻塞。

⇒ **U9 提出的"排队（libuv 线程池）"假说被证伪**（这是本批第 6 条被我自己的仪器否掉的解释）。同一批样本里 `resolve` 仍要 ~100 ms，而**文件读本身是 0.2 ms、池是空的、循环是健康的**。

## 三、因此剩下什么（**新假说，未验证**）

按排除法，剩下的载体是**数据库引擎**：同一进程内所有 Prisma 查询都走**同一个引擎进程/连接**，而它有自己的内部队列。若引擎正忙于其他查询（例如启动期的 `listFiles` 扇出 —— 实测 51 次 × 2 次查询），一次 acquire 的 `queryMs` 就会**排在引擎队列里**，而：

- 文件系统金丝雀**不受影响**（不同资源）→ 与实测的 0–1 ms 相符；
- 事件循环**保持健康**（异步等待）→ 与实测的 0 相符；
- `queryMs` 在 21–336 ms 之间大幅浮动 → 与"队列深度随时刻变化"相符。

## 四、下一步判据（写死；仪器模式已被 U10 验证）

照搬金丝雀模式到数据库：`startDbCanary()` = 与 acquire 同时启动、在其后 await 的一次**平凡查询**（例如 `artifactVersion.count()` 或 `SELECT 1`），并把 `dbCanaryMs` 加进慢报告。
- 若 `dbCanaryMs` 同样 ~100 ms ⇒ **引擎队列饱和**（与应用自身的扇出竞争）⇒ 优化方向是**减少并发/扇出**，与 `listFiles` 那条同源；
- 若 `dbCanaryMs` 只有几 ms ⇒ 引擎不饱和，回到这条特定查询/路径继续查。

## 五、诚实边界

1. 3 个样本、单次运行、dev 构建；本轮的 `resolve` ~100 ms 比 U7 的 220–521 ms 小，量级随运行变化（已知）。
2. 金丝雀是**页缓存热**的 1 KB 文件 —— 它测的是"池/队列"是否饱和，不是"磁盘首读"延迟（后者已由 U9 的 dd/readFile 直测覆盖）。
3. 在途计数只统计**经过我埋点的那段**（acquire 的 resolve+stat），不统计应用其他地方的 fs 操作；因此"1–2"是**下界**，但足以排除饱和（饱和时金丝雀必然慢）。
4. **未做任何优化。**
