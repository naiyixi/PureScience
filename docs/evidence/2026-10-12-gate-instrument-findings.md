# 门禁仪器：一次不可归因的运行 + 两处脚本缺陷（2026-10-12）

> 起因：为 v2.0.0 首发跑 `release-gate.sh <sha>`，汇总行给出 `typecheck:node|FAIL`、`vitest|FAIL`。
> 本文件记录**为什么那次判决不可用**、**脚本被修了什么**、以及**独立重跑的干净读数**。

## 一、那次运行不可归因（证据在日志自己的版本戳里）

```
=== typecheck:node ===
> purescience@2.0.0 typecheck:node        ← 被测提交（门禁工作树）
> tsc --noEmit -p tsconfig.node.json --composite false
=== typecheck:web ===
> purescience@1.102.0 typecheck:web       ← 主树的版本（已回退后的状态）
```

**同一次运行里的各环跑在两个不同的树里**。成因是**我在门禁运行期间动了主树**（回退发版提交、
外加一次 `git worktree prune`）。按纪律：**输入在运行中变过的读数不能用** —— 它既不能读成"树是红的"，
也不能读成"绿"。

## 二、脚本的两处缺陷（已修）

1. **失败明细被丢掉**：`local out=$("$@" 2>&1)` 把整段输出收进局部变量、只 `tail -6` 打印 ⇒
   出现 `typecheck:node|FAIL` 而**拿不到任何原文**（我搜 `error TS` 一条都没有；非零退出且无输出，
   正是"命令崩掉时它的输出不是判据"的形状）。**修**：每环全文落
   `/tmp/release-gate-<sha8>-<环名>.log`，失败时额外把该环**尾部 40 行**烤出来，汇总行带上全文路径。
2. **"不同树跑同一批环"不可见**：**修**：每环开头自证一行 `[ring] cwd=<目录> version=<package.json 版本>`。
   今天这种"两环两个版本号"的情形本来要靠人从输出里反推。

## 三、独立重跑（干净工作树，HEAD `7cccf71b`）

| 环 | 读数 |
|---|---|
| `vitest`（全量，`--maxWorkers=4`，隔离工作树） | **1248 文件通过 / 16 skipped**；**16131 passed / 0 failed** / 207 skipped |
| `typecheck:node`（隔离工作树） | **exit 0**，`error TS` 计数 **0** |
| `typecheck:web` | 同次改动已在提交前验过 **exit 0** |
| `eslint`（门禁那次） | **0 error / 122 warning**（基线 140 ⇒ 本批未新增，且更少） |
| `repo-checks`（门禁那次） | **全部通过** |

⇒ **当前 HEAD 五环皆过**；门禁那次的 FAIL 属于被搅过的运行，**不是树的状态**。
（写下来是为了防止将来有人把那次 `FAIL` 当成"树红"去查一个不存在的问题。）

## 四、给下一次发版门禁的三条硬要求

1. **门禁运行期间不动主树**（不 revert、不 prune、不 `git add`）；要动就等它跑完。
2. 结果只认**汇总行 + 每环全文**（后者现在有了固定路径），红了的下一步是读该环原文定因。
3. 门禁在**要打 tag 的那个提交**上跑；并发执行器的在制品不进工作树（隔离工作树天然满足）。
