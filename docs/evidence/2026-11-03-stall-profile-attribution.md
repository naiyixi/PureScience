# 事件循环停摆的归因读数：采样帧不是「谁占着循环」

**日期**：2026-11-03　**取数**：本机 `~/Library/Logs/PureScience/main{,.1,.2}.log`（5 天，2026-10-28 → 11-02）
**工具**：`npm run diag:stalls`（新增，`scripts/stall-profile-report.mjs`，自带 `--selftest`）
**结论一句话**：停摆行里的 `stack.frames` 记的是**循环回来以后先跑了什么**；本轮量到采样帧只能解释停摆墙钟的 **17%**，其余 80% 是「进程根本没在跑」，所以按 `frames[].samples` 排序会把一个成本 0.1 ms 量级的函数读成头号元凶。

| 已观测主线程时间           | **4,386.0 s = 17%**                                                                                               |

| 带剖面的 / 不带剖面的      | 2,292 / **1,914**                                                                                                 |

7 小时里有 6 小时是「进程没在跑」——这段时间里没有任何采样帧能解释它，而这正是 `fs-queue-saturated` 这个成因的物理含义（磁盘/内存子系统在换页，主线程拿不到 CPU）。

## 二 被否掉的假设：`renderAppMcpToolReferences` 是「占着循环」的第一名

按 `frames[].samples` 求和，第一名是 `renderAppMcpToolReferences`（三个 bundle 版本合计 **6,895 个样本 / 44% 份额**，出现在 872 条事件里，每条事件里它通常还是样本最多的那一帧）。它看起来正是一个「每回合都在跑、做字符串替换」的可疑对象，改它有明确收益（14 个服务器 × 2–3 个别名 `replaceAll` + 49 条 `new RegExp` 逐条替换）。

**实测把它否掉了。** 用生产函数本体（不是复刻）、esbuild 打包成 ESM 后跑基准：

| 文本大小 | `claude-code` | `opencode`  | `codebuddy` |
| -------- | ------------- | ----------- | ----------- |
| 4 KB     | 0.056 ms/次   | 0.159 ms/次 | 0.053 ms/次 |
| 20 KB    | 0.119 ms/次   | 0.083 ms/次 | 0.079 ms/次 |
| 60 KB    | 0.144 ms/次   | 0.139 ms/次 | 0.141 ms/次 |
| 200 KB   | 0.573 ms/次   | 0.510 ms/次 | 0.510 ms/次 |

即：线性约 **2.6 µs/KB**，200 KB 的系统提示也只花 0.5 ms。要凑出中位一次 1.9 s 的停摆，需要它在一条事件里被调用 ~3,700 次——而它只出现在「准备好提示词」的那几处（`ctx.systemPromptAppends` / `ctx.turnPromptReminders` 各一次 `.map`）。所以样本份额反映的是**它恰好在循环恢复后的第一段工作里**，不是它把循环占住了。

## 三 为什么它会看起来像第一名（仪器口径）

- V8 采样器只有在主线程**重新拿到 CPU** 时才出样本；`unobservedMs` 把「没在跑」的那段单独记走，`frames` 只覆盖剩下的 17%。
- 每条停摆里它大约 **8 个样本**（≈8 ms），相对于 1.9 s 的中位停摆是 **0.4%**；而「样本总数第一」这个读法把 4,206 条事件加总，于是一个「每条事件都在场、每次只占几毫秒」的函数，在总量上压过了真正偶发但很长的持锁者。
- 正确读法是三列并排：**事件数 / 每事件样本数 / 占已观测时间的份额**，并且先读「已观测份额」这一行。新工具默认就按这个口径打印，并在表尾写明这句。

## 五 边界（不许读成更强）

- **这不是「谁占着循环」的定因工具**。它能说「采样帧解释不了 80% 的停摆墙钟」，不能说要怪谁；真定因需要的是主机侧读数（本条日志里已有）与 `fs` 队列的可观测性，而不是 JS 帧表。
- 单机、单人、且这 5 天里本机在跑构建与测试（`loadAvg1m` 峰值 587 就是在这样的时段出现的）⇒ 这些数字描述的是**开发机**，不是用户机；不许据此声称用户端体感。
- `windowMs` 是看门狗自己判定的窗口宽度，`fs-queue-saturated` 的 `basis` 里那个 `canaryMs` 是**排队等待**，不等于 CPU 时间。
- 本轮**没有产品侧改动**：既不声称变快，也不声称找到了那个「占着循环的人」。
