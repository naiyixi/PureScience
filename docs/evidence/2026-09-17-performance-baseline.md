# 流畅度实测基线（2026-09-17，真实实例 / 真实数据）

用户反馈"卡"。按"先量数字再谈优化"做基线，**全部数字来自运行中的真实实例与真实数据根**（`~/.purescience-project`，59 个会话 / 51 个项目目录 / `sessions` 共 **60 MB**）。

## 一、基线数字（同一进程、连续多次调用）

| 动作 | 实测 | 说明 |
|---|---|---|
| **`sessions:load-all`（会话目录整体加载）** | **1671 / 1302 / 1360 / 1366 / 1492 ms**（中位 ~1366） | 每次调用都这个量级，**看不到缓存** |
| ↳ 该通道**返回体量** | **55,371,532 B ≈ 55 MB** | 一次"列表"调用返回 55 MB |
| ↳ 磁盘上对应 JSON | 62,919,464 B ≈ 63 MB | 源数据规模 |
| ↳ **同样这些字节从磁盘读**（page cache） | **10 ms**（59 文件 / 62.8 MB） | ⇒ 瓶颈**不在 I/O** |
| `search:query`（中文"稳定性"） | **1169 ms 首次 / 62 / 69 ms 之后** | 索引预热后 ~65 ms，可接受 |
| `artifacts:list-project-files`（产物+未发布条目） | 72 / 39 / 37 / 46 / 56 ms | 可接受 |
| 启动协调 `session-hydration`（日志实测） | **1270 / 1359 / 1604 ms**，启动那趟曾见 **6754 ms** | 每趟都遍历 59 个会话 |

## 二、烟枪：一次"列表"调用搬 55 MB

- `load-all` 的中位 **1.37 s**，而**同样的 62.8 MB 从磁盘读只要 10 ms** ⇒ 时间花在**解析/归一化/序列化**这 60 MB 上，而不是读盘；
- 返回值 **55 MB** —— 一个"会话目录"接口把**全部消息体**一起吐回来。这就是"卡"的最大嫌疑：任何需要会话列表的路径（启动、切换、刷新）都要付这笔钱。

## 四、结论与下一步（优化是独立单元，先立案）

**结论**：`卡` 的第一嫌疑是**会话目录一次性搬运 55 MB / 1.3 s**，且启动那趟还要叠加协调（1.3–6.7 s）。I/O 已被排除（10 ms）。

**下一步（v1.64，带验收口径）**：
1. **列表不再返回全部消息体**：`load-all` 只回摘要（标题/时间/计数/最后一条片段），消息按需拉取 —— 验收：该通道响应 **< 2 MB**、耗时 **p95 < 150 ms**（同一数据根、同一量法复测）；
2. **目录级缓存 + 变更事件失效**（`session:created/updated/deleted` 已有事件面）—— 验收：连续两次调用第二次 **< 20 ms**，且改动后能立刻反映（用例 + 真机各一次）；
3. **启动协调增量**：只处理自上次水位以来变化的会话 —— 验收：启动那趟 **< 1 s**（59 会话数据根）。
4. **渲染层**：另起一次带窗口实例的 CDP 采样（切页 / 滚动 / 大列表），把"用户感受到的卡"也变成数字。
