# doctor 报出两条数据根与各自解析命中率（2026-11-05）

> 立案来源：`docs/evidence/2026-11-05-case-ranking-count-semantics.md` §6 末尾那条遗留事实 ——
> 同一台机器上开发构建与打包应用各有一份数据根，而 CLI（未打包）默认读开发根。谁在开发根上读案例计数，
> 就会看到「有行、磁盘没有」。当时判定：根不该由 CLI 猜，要消除它得让 doctor 同时报出两条根与各自命中率。

## 1. 交付

| 面          | 落点                                                 | 说明                                                                                               |
| ----------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 测量模块    | `packages/purescience/data-roots.mjs`                | 逐个根报：库在不在/多大/最近写入、`ManagedFile` 行数与存活行、抽样 `storageKey` 在本根下能解析几个 |
| doctor 检查 | `packages/purescience/doctor.mjs`（`data_roots`）    | 检查项 + 报告里的结构化 `dataRoots` + 逐根一段的可读输出                                           |
| 文档        | `packages/purescience/CLI.md`（Data roots (doctor)） | 三种状态的区别写在文档里，读者不必读源码                                                           |
| 测试        | `packages/purescience/data-roots.test.ts`（9 项）    | 含「没有库 ≠ 0 行」「打不开 = 未测量且报出原因」「越界 key 不算缺失」三条                          |

## 2. 本机真读数（2026-11-05 04:3x，只读）

`node packages/purescience/cli.mjs doctor`，退出码 `0`：

```
  [warn] data_roots  roots=2 withDatabase=2 measured=2 unresolved=dev:0/20 detail=这些根里有行，但抽样的 storageKey 在本根下找不到字节：读数要连同根一起看

data roots (2):
  dev  /Users/totota/.purescience-project  db=83.8 MB  rows=496  live=470  resolvable=0/20  last write=2026-10-30T03:40:33Z
  prod /Users/totota/.purescience  db=421.5 MB  rows=1176  live=1176  resolvable=20/20  last write=2026-11-04T15:54:31Z
  未打包的 CLI 默认读 dev 根，打包后的应用读 prod 根；命中率是抽样出来的：那一根里的 storageKey 有几个能在同一根下找到字节。
```

读法（与上一份证据档的结论一致，这次是产品自己算出来的）：

- **dev 根**：496 行、470 条未删、抽样 20 条 **0 条**能在本根下找到字节，最后写入停在 10-30 —— 开发根早已不再写，
  它的行指向的字节不在这里。
- **prod 根**：1176 行全部存活、抽样 20 条 **20/20** 命中，最后写入 11-04 15:54Z —— 打包应用正在用的就是它。
- 因此「126 行 vs 0 文件」不是数据丢失，也不是索引脱节：**是在 dev 根上问 prod 根的事**。这条结论现在由一个
  可复跑的命令给出，不再依赖某一份库的手工比对。

## 3. 三种状态为什么要分开

| 状态           | 含义                                                      | 反例（若合并会怎样）                               |
| -------------- | --------------------------------------------------------- | -------------------------------------------------- |
| `no-database`  | 根存在但没有数据库文件；行数报**缺席**，不报 `0`          | 报 0 会让读者以为「查过，确实没有」                |
| `not-measured` | 库在，但这个运行时打不开（原因逐条打印）                  | 报 0 会把「读不到」伪装成「没有」                  |
| `rows`         | 查询真的跑了；`live` 在所有行都删除时为 `null` 而不是 `0` | `SUM` 空集是 NULL，写 0 是把两种不同的答案合成一个 |

另有一条判据：`storageKey` 为绝对路径、或含 `..` 时计为 `outsideRoot`，**不算 missing** —— 那不是这一根欠它的字节，
而是这条行从来不指向这一根。

## 4. 边界（不许读成更强）

- 只读：`DatabaseSync` 以 `readOnly: true` 打开，读完即 `close()`；不建表、不写任何根、不动设置。
- 不判定就绪：doctor 的老规矩未变，就绪结论只由 `purescience ready` 给（输出末尾那句仍在）。
- 抽样是代理指标：20 条只够区分「这套 key 在这一根下成立」与「不成立」，不是全量校验；比率不当作完整度。
- 未取证：`--json` 输出的完整样例未在 Windows 上跑过；`node:sqlite` 在 `>=22.5.0` 上是实验特性（本机 22.22.3 可用），
  更老的运行时走 `not-measured` 分支并打印原因（有单测，无真机读数）。
