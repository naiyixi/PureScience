# macOS x64 打包冒烟：三次读数、两种形状，判为机器侧

日期 2026-11-07（执行器轮次）。对象：`scripts/macos-package-smoke.mjs`，作业 `build / Build macos-x64`
（runner 标签 `macos-26-intel`）。

## 一 为什么又查它

`Nightly` 在两次相邻提交上都红在同一步，且红的两条都是「签名读数没取到 ⇒ 门按设计拒收」。按纪律先读**作业级**
日志，而不是把下游那句 `macSignature=unproven` 当根因——它只是「冒烟没跑完」的后果。

## 三 归因

1. **不是签名/公证**。四条的失败步骤里，「Enforce the macOS Developer ID signature gate」永远是第二环；
   第一环是冒烟本身。签名门那句 `unproven` 是这个后果的正确表达（未观测不得记作通过）。
2. **不是本笔的代码面**。`08efb017` 只动诊断段与计划档（9 个文件，零 `scripts/**`、零打包路径）；
   `f08e7fb3` 只改一条测试用例的平台固定。同一提交的 `Build macos-arm64` 冒烟**passed**。
3. **复跑换了停点**，这是决定性的一条：同一份产物、零代码改动，一次卡在模块加载期（57 s+ 无进展），
   一次走到端点宣告后卡在 HTTP 应答。两处都在「主进程已经起来、但服务不可用」这一段，而停点不同
   ⇒ 读作 runner 侧间歇，不读作某一处代码的确定性缺陷。
4. **本机无法复现**：本机是 arm64，跑不了 x64 包。因此这一条按「未在本机复现」记，不写成「已排除」。

**判决**：macos-x64 打包冒烟在 `macos-26-intel` 上是间歇红（两种形状），不由本批改动引入，也不由重跑消除。
按纪律不加大超时（60 s 相对健康基线 15–25 s/次启动并不在刀口上），也不把「作业绿过」当作结案。

## 四 下一步（留给下一轮，不在本笔）

- 仪器：`launchAndProbe` 的 `fetch(... /api/bootstrap)` 超时目前只抛一句 `The operation was aborted due to
  timeout`。该分支应具名到「端点 + 端口是否可连 + 应用输出尾巴」，与 2026-10-27 那轮对启动超时做的分离同形
  （`docs/evidence/2026-10-27-macos-smoke-timeout-instrument.md`）。这是**仪器**改动，不是产品改动。
- 判据：同一提交上再出现三次同一形状，才升级为产品侧立案；否则维持「机器侧间歇」并按仪器输出逐次记档。

## 五 边界

- 本文不主张 x64 包本身「没问题」：它只说明这四次红绿**归不到本批提交**，且停点不唯一。
- 重跑命令只用于 Nightly（无发布资产）；发布窗口里仍按既有结论「不重跑单个作业」。
