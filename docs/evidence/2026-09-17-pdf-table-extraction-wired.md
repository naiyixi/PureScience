# PDF 表格抽取：从"建好未接线"到真机跑通（2026-09-17）

## 一、接线的起点（一个被忽略的事实）

`src/shared/pdf-table-extraction.ts` **早已存在**：几何法（`text-layer-row-column-clustering`）与纯文本法（`text-layer-whitespace-clustering`）、`confidence`、`toMarkdownTable`/`toTsv`、审计标签 `candidate-extraction` / `verify-against-source`、12 个测试。**但生产调用者为 0** —— 按本仓"没有生产调用者的组件不算完成"的规矩，它不算做完。本单元把它接到真入口，而不是重写。

## 二、接线内容

| 环节 | 改动 |
|---|---|
| 解析层 | 采集每页**带坐标的条目**（`x/y/width/height`），随 `pages` 一起返回；**纯文本路径一字未改**（参考文献导入不受影响） |
| 服务层 | `PdfService.tables(docId, page?)`：几何优先、无坐标时退到纯文本法，每条候选带 method/confidence/markdown/tsv/warnings，上限 8 条 |
| 契约 | `PDF_TABLES_TOOL_NAME='pdf_tables'`、`PdfTablesResult`/`PdfTableCandidateForAgent` |

| 全链 | `pdf:tables` 通道 → 应用命令 → host 处理器 → local RPC 分支 → ipc 适配器 → **preload 方法 + 类型** |
| 契约级联 | 目录条目 + `npm run gen:web-api-map` + 各处 count pin（catalog/surface-inventory/preload/命令清单/参数形态） |

## 三、真机过程中抓到的两个缺陷

### 3.1 "跑通了却什么也没抽到"（已修，`5914e77`）

真机第一次（两份 app 自产 PDF）与第二次（matplotlib 生成的**真表格 PDF**）都是 `candidates = []`。**用测量代替猜测**：

- 临时诊断（跑完即删）直接喂解析出的条目给抽取器 ⇒ **1 条 high 置信候选**；
- 同一份文件走生产路径 `PdfService.tables()` ⇒ **0 条**。

⇒ 差异在我的接线：`parsePdf` 的 `return` 里**没有带上 `items`**（我先前那次文本替换打到了另一处同名 return），于是服务退回到**弱方法**，而 pdfjs 的文本层永远不满足"两空格分列"。**条目被采集后又丢在了下一行。**

修好后 in-process 复验：`direct 1 / service 1`，`method=text-layer-row-column-clustering`、`confidence=high`、`rows=7`、warnings 两条齐全。

### 3.2 列聚类切太碎（**未修，立案**）

真机第三次（agent 真调用工具）返回 **1 条候选**，但 mardown 形态是：

```
| Gene |  |  |  | log2FC |  | padj |  | Cluster |  |
|  |  |  | MYC |  | 3.42 |  | 1.2e-12 |  | 0 |
|  | CDKN1A |  |  |  | -2.87 |  | 4.5e-09 |  | 1 |
```

**表是 4 列，候选是 10 列** —— 因为表头的 x 位置与右对齐数字的 x 位置不同，被当成不同列。agent **原样回报、拒绝自行重组**（符合"候选不是转写"的定位），但这说明聚类需要一遍**合并**：相邻列若**从不在同一行同时有内容**，它们多半是同一个逻辑列被切开的。

⇒ 立案为下一单元（带用例：真表格 PDF 应得 4 列；同时要防"稀疏表的合法空列被误合并"）。**在修好之前，我不会把这条 capability 说成"可用"** —— 它现在能出候选，但列切分对本机生成的真表格是错的。

### 3.3 列合并：做了第一遍（`dad908a`），**仍未达标**

第一遍合并规则：**相邻锚点若从不在同一行同时有内容 ⇒ 同一逻辑列**（真列对至少会在一行同时被填满），外加"距离不得超过半个列距"的护栏（防止"稀疏表 A 列只在这些行、B 列只在那些行"被无限合并）。

**实测效果（同一份真表格）**：10 列 → **5 列**，四对里合了三对；值一个没丢、顺序仍是页面顺序（这两条已写进用例作为**阅读契约**）。

**仍差一列，原因量清了**：matplotlib **居中排版**，基因名长短不同 ⇒ 起始 x 各不相同（`MYC` 63.5 / `CDKN1A` 54.6 / `GAPDH` 58.0），锚点聚类也被切碎。要把 5 收敛到 4，需要把列模型从"按起始 x 聚类"换成**按列中心/列距聚类**，或做带共现约束的**传递合并**——这是独立设计任务，不塞进本遍。

⇒ 结论照旧：**不称"可用"**。它现在能出候选、值不丢、顺序不乱、并带 `verify-against-source` 审计标签；**但列数是错的**，而列数错会让"按列取数"这类用法出错。下一单元：列模型（按中心聚类 + 传递合并 + 稀疏表守卫），验收口径=真表格 PDF 得 4 列。

### 3.4 传递合并（`08da188`）：夹具达标，**真机仍未达标**（如实记）

修法：合并后**原地重试**同一列（一列被切成三个锚点需要两次合并，之前合完一对就前进，所以停在 5 列）。

- **夹具（同一形状，3 行数据）**：**4 列达标**，表头 `['Gene','log2FC','padj','Cluster']`、MYC 行 `['MYC','3.42','1.2e-12','0']` 精确匹配 ⇒ 写进用例作为验收。
- **真机（同一份 PDF，6 行数据）**：**仍是 5 列**，且形态是"表头 `Cluster` 在第 4 列、数值全落在第 5 列"的错位——**agent 自己就指出了列对齐可疑**，并引用了工具自带的那条 `verify-against-source`。

**差距原因（初步）**：夹具是我从**更早一次**真机调用 dump 下来的条目构的（4 行），真机这份有 6 行、锚点分布更宽 ⇒ 夹具**不能代表**真机。⇒ **验收口径在真机上未达成**，我不拿夹具冒充达标。

### 3.5 达标了（`30619c8`）：真机 **7 行 × 4 列**

按上一节的口径做完两步，**验收在真机上达成**：

1. **dump 真机条目**（临时诊断，用完即删）拿到真机的 10 个锚点与每格跨度；根因量清：护栏用"最宽锚点间距"估列距，而**居中排版把它撑大**（估算 34.4 vs 实际需要跨越的 43.7），于是 `Cluster` 那对（表头 284.2 / 数值 327.9）被挡住。
2. **护栏换成有原则的量**：同一列的两个锚点，其**单元格跨度之间的空隙**不应超过**拆格阈值**（拆格用 `> 12` 判新格，合并就用 `≤ 12` 判同列）——同一个量、两个方向。共现判据（**任一行同时填满两列 ⇒ 不是同一列**）仍然必须成立，它才是防止稀疏表被合并的那道闸。
3. **夹具换成真机同源**：把测试夹具直接换成真机这份 PDF 的 **28 个定位条目**（6 行数据），不再用手搓的近似版——上一遍正是"夹具过、真机不过"。

**真机复验（agent 真调用工具链）**：

```
候选条数：1
7 rows × 4 columns
| Gene | log2FC | padj | Cluster |
| --- | --- | --- | --- |
（带 candidate-extraction / verify-against-source 警告）
```

⇒ 列模型**达标**：真表格 PDF 得 4 列，表头与数值同列。**但"可用"仍是有保留的**：这条能力是**候选**（工具自己写明 `verify-against-source`），且以上达标只覆盖**矢量文本表格**这一类；两份 app 自产 PDF（文本表格或图片表格）仍是 0 候选——那是方法边界，不是缺陷。
