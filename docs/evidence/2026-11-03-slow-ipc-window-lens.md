# 慢 IPC 的「窗口」视角：一次忙碌被逐行汇总读成了 N 个慢通道（2026-11-03）

> 起因：台账 §279 留下的下一单元是「`notifications:get-snapshot`（中位 740 ms）与 `artifacts:read-preview`
> （中位 482 ms、成对出现）都只有日志分布、没有归因，先量再改」。本节就是那次「先量」的读数与结论 ——
> 结论是**这两条都不该单独开单元**，而取数用的那张「按通道」的表本身就是偏差来源。

## 一 取数口径

- 数据：本机 `~/Library/Logs/PureScience/main.log` + `main.1.log` + `main.2.log`（打包/开发实例都写这里），
  窗口 **2026-10-28T06:48Z → 2026-11-02T16:45Z**，行来源 `msg = "ipc handler was slow"`（阈值 50 ms）。

  换 `--gap` / `--min-peers` / `--exclude` 可复算。

## 三 被否掉的两条假设

1. **「read-preview 成对出现 = 同一份被读多遍，所以加单飞/去重」——不成立。**
   09:53:30 那一簇 7 行的同一窗口里，邻近的 `artifact version resolve was slow` 记录给出的 `bytes` 是
   5546 / 5188 / 30490 / 5662 / 5111 / 30444 / 5188 —— **多份不同产物在同一秒被点开**（另有 5188 重复一次）。
   以「重复请求」为前提去做缓存/单飞，会为一个没有证据的成本写一层新机制；而真正被读数支持的是
   「同一秒里开了很多份」。`artifacts:read-preview` 的 110 行里 90% 落在 ≥3 条慢处理器的窗口里，
   它自己的全额时间只占慢行时间的 0.5%。
2. **「get-snapshot 中位 740 ms，值得单独优化」——量级不支持。**
   87 行、占 1.6%，20–30% 才落在忙碌窗口里（多数是它自己在等），且最大两条（120.5 s、151.9 s）是整段循环停顿
   （`cpuShare 0.071` / `0.061`），不是快照本身的计算。

| 位置                           | 内容                                                                                                                                                                                                      |

| `scripts/slow-ipc-windows.mjs` | 窗口归并 + 每通道 `window-borne`/`mixed`/`self-borne` 三态判词 + 最大窗口表；`--exclude` 用来把 turn 类（`acp:send-prompt` 的耗时就是回合长度）从「阻塞时间」里拿掉，排除的条数**具名打印**（0 条也打印） |

## 五 边界（不许读成更强）

- **不是窗口读数**：全部来自日志里已有的 50 ms 阈值行，**低于阈值的一次调用不在样本里**；因此「占比」是
  「慢行时间里的占比」，不是「主进程时间里的占比」。
- **本机单机**：CI runner 与其他用户机器的分布未取。
- **窗口是参数，不是事实**：`--gap` 从 300 改到 3000，段数从 3,457 变到 1,306；判词给出的三态在三种 gap 下
  对这两条通道稳定（read-preview 90/90/100%、get-snapshot 20/30/30%），但**别把段数当客观量**。
- 逐行 `cpuMs` 是**进程级**（`process.cpuUsage()`，含所有线程），所以同一窗口内 N 条行的 `cpuMs` 会被重复计入 ——
  这正是「把一次忙碌读成 N 份成本」的成因，修的是读法，不是那条日志。
