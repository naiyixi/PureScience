# 图六 / 图七 对照结论（2026-11-23）

对照的是截图里那套「场景模型 + 本地解析模型」的科研工作台。分三类写：**已有且真能用**、**已有但有一句免责声明在替它兜底**、**完全没有**。

## 一、场景模型（图七）

我们的设置页确实有这一组：主模型 + 场景模型（子智能体 / 审查 / 视觉 / 会话上下文…），
消费端也在：`visionModel` 由 `settings/vision-model-owner.ts` 与 `acp/image-input-compatibility-owner.ts`
真正使用（本轮刚修好「配了视觉模型仍被挡在图片外」）。

**但有一句免责声明**（`settings.scenarioModelCaveat`）：框架经 ACP 运行时，子智能体与审查的独立模型
可能受框架限制无法逐会话下发，此时回退主模型。

这正是「能选，但不一定真用」的位置。按「让布局解释」的规矩，一句话盖住四行的真实状态不合格 ——
应该变成每行自己带状态：能下发就正常，不能下发就在该行直接标「此框架不支持，将使用主模型」，
而不是在整块底下写一段小字。

## 二、图像生成模型（图七）

**完全没有。** 代码里没有任何 image-generation 设置项，也没有调用端点；`visionModel` 是「读图」，
不是「出图」。要做到截图那种「图像生成可以跟主模型分开配」，等于新增一条能力链：
设置项 → 端点枚举（各家 images API 形状不同）→ 生成请求 → 产物落 Artifact、记 provenance。
**不是 UI 活**，按功能立项做，不冒充已有。

## 三、提示词优化（图七）

**完全没有。** 没有 prompt-optimize 服务，也没有相关设置。同样按功能立项。

## 四、本地解析模型（图六）

- 清单 `resources/model-weights/manifest.json` 里**只有一个条目**：`structure-recognition-primary`
  （298,662,033 B，DECIMER，化学结构式 image→SMILES）。
- 引擎侧真正被使用的也只有这一路：`engines/structure-recognition.ts` → `pdf-service.recognizeStructure`。
  本轮实机读数：DECIMER 2.7.2 / pypdfium2 5.14.0 / rdkit 2026.09.1 均可用；MolScribe 缺 checkpoint。
- 清单里声明的 `document-parse`、`illustration`、`fallback-engine` 三种 **没有任何消费者**：声明了但没接线。
  科研格式（PDF 表格/正文、DOCX、补充材料）走的是另一套（pdf-service 的文本/表格读取），
  与「本地大模型解析」不是一回事。

**结论**：截图那套「各种科研格式的本地解析」我们**没有对等物**。现有的是化学结构识别这一条窄而深的链路，
它确实在用（有实机读数），但不能被说成「科研格式解析」。

## 五、按优先级的立案

| 项 | 类型 | 判据（缺一不算完） |
| --- | --- | --- |
| 场景模型每行显示真实可用状态 | UI（小） | 受框架限制的行带状态说明；文案不再靠底部一段小字兜底 |
| 权重走自家镜像 | 工程（进行中） | `models-v1` 资产与 `runtime-v1` 同规则：自家主机在前；sha256 与清单逐位相同；公网 200 且长度相符 |
| 图像生成模型与主模型分离 | 功能（大） | 能选到与主模型不同的生成模型；一次真实生成落 Artifact 并带 provenance；失败有具名原因 |
| 提示词优化 | 功能（中） | 一个可开关的优化步骤，产物可对照（优化前/后），不开就是原样 |
| 文档解析本地模型 | 功能（大） | 清单里 `document-parse` 有真实条目 + 有消费者 + 一次真实 PDF/DOCX 导入走本地模型并给出结构化产物 |
