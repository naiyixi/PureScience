# U2：Files 读取 211 ms 里，闸门 0 ms、查询 211 ms（真机 dev 实例，含自杀式证伪）

- 日期：2026-09-18
- 实例：`electron-vite dev` 带窗口，独立端口 44105 / 独立 profile / CDP 9336；语料为真实数据根副本（59 会话 + 产物树硬链）
- 起点（U1 的结论）：主进程在几乎空闲的一趟里有 **135 次 ≥50 ms 的 IPC**，其中 `project-files:list-files` **102 次**、单次 95–150 ms；`preview-resources:acquire` 5 次、单次 ~370 ms。
- 本单元新增的两处仪器（**已随提交落地**）：
  1. `project-files` 的四个读取入口全部走 `timedRead`：把一次读拆成**恢复闸门**与**查询**两段，≥50 ms 记 `project files read was slow {operation,totalMs,recoveryMs,queryMs}`（不带任何请求内容）。
  2. （U1 已落地的）`application-command-router` 慢 handler 与 `diagnostics/ipc-rejection` 慢 IPC 计时。
- 用例：`project-files/ipc.test.ts` 新增一条（快读不记、慢读按 80/120 拆出 200）。

## 一、实测（启动窗口就足以说明）

`listFiles` 慢读 **51 次**（仅应用启动阶段，我还没驱动任何交互）：

| 指标 | 值 |
|---|---|
| 单次总时长（中位） | **211 ms** |
| 其中 **恢复闸门**（`recoverPendingDeletions`） | **0 ms** |
| 其中 **查询**（`repository.listFiles`） | **211 ms（100%）** |
| 51 次累计 | **10,822 ms**，其中闸门 **3 ms（0%）**、查询 **10,819 ms** |

## 二、被我自己证伪的那条线索（必须留档）

看代码时我最强的怀疑是：**每个 Files 读取都以 `await recoveryBackend.recoverPendingDeletions()` 开头** —— "一个恢复闸门挂在每次读上，多半就是它"。仪器把这条**直接否掉了**：闸门中位 **0 ms**（无待恢复项时立即返回），代价 **100% 在查询**。
⇒ 若不装这个拆分仪器，我很可能把优化做在闸门上（例如加缓存/去掉调用），**方向完全错**。这条比结论本身更值：**"读代码得出的强假设，必须用能分辨两段的仪器去验"**。

## 三、确定的靶子（下一单元 U2b）

`repository.listFiles()` 单次 **~211 ms**（`project-files/query-support.ts` / `repository.ts`），被 **每项目一次**地调用（Home 页给每个项目卡片取文件列表以渲染类型标记，`HomePage.tsx:245`）。因此启动期的代价是 **211 ms × 项目数**（本机 59 会话 / 50 项目 ⇒ 实测 51 次 ≈ 10.8 s 的主进程工作）。

**U2b 要回答**（判据都可就地量）：
1. 211 ms 花在**哪一段**：SQL 查询本身 / 每行 `stat` 文件系统 / N+1 查询 / 行映射？
2. 是否**可复用**：同一次启动里 50 个项目各查一次，是否存在重复的公共前缀（例如 project 元数据、artifact 组）可一次取回？
3. 渲染侧是否**真的需要**每个项目的文件列表（Home 只展示文件类型 chip —— 也许只需一个"有哪些类型"的聚合）。

## 四、诚实边界

1. dev 构建；打包版同表未采（趋势与 U1 一致）。
2. 单次运行、单语料规模（59 会话 / 50 项目）；"211 ms"是这台机器上的这一份语料，不是普遍常数。
3. 阈值 50 ms；阈值以下的读没有被记录，所以"51 次"不等于"总共只有 51 次读"。
4. **未做任何优化**：本单元只交付"哪一段慢"的判据与仪器。
