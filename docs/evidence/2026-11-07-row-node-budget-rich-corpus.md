# 富 markdown 语料下的每行节点数（2026-11-07）

> 上一份 `2026-11-06-row-node-budget.md` 立尺子时用的是**单句回复**，于是 `body=3` 是下界、`chrome 占 90%`
> 是上界，档内自己把「让夹具产一份富 markdown」写成**具名未办**。本档补齐那一步：夹具按标记产出富回复，
> 同一把尺子重取 40 / 160 两档，并给「body / chrome 哪一半值得动」一个带数字的答案。**只改仪器与夹具，
> 不改产品代码，也不声称变快。**

## 一 两处改动

1. `e2e/fixtures/fake-opencode.mjs`：新增 `RICH_MARKDOWN_PROMPT` 标记与一份富回复（二级标题 + 三条目列表
   + 带语法的 python 代码块 + 3×3 表格 + 引用块 + 收尾句，1,890 字符）。**只有含该标记的 prompt 拿到它**，
   其余规格的回复逐字不变（默认回复仍是那句 `Deterministic reply: …`）。
2. `e2e/perf/render-count.spec.ts`：
   - `PERF_RICH_MARKDOWN=1` 让回合发带标记的 prompt；`[row-nodes]` 行首打印 `corpus=`，读数不能再被误认成
     另一份语料。
   - **修一处中位数口径错**：原来对**全部行**取一个中位，可 agent 行与用户行的节点预算不是一回事
     （实测 152 对 19）。混合中位只回答「哪种行更多」——上一份的 `median=31 (body=3 chrome=28)` 就是这么来的，
     31 既不是 agent 行也不是用户行。现在按 `data-slot` 分成 agent / user 两类，各自给中位与 body 占比。

跑法（同一份 e2e 产物，四条命令）：

```
npm run build:e2e
PERF_TURNS=40  npx playwright test e2e/perf/render-count.spec.ts --reporter=line
PERF_TURNS=40  PERF_RICH_MARKDOWN=1 npx playwright test e2e/perf/render-count.spec.ts --reporter=line
PERF_TURNS=160 npx playwright test e2e/perf/render-count.spec.ts --reporter=line
PERF_TURNS=160 PERF_RICH_MARKDOWN=1 npx playwright test e2e/perf/render-count.spec.ts --reporter=line
```

## 三 结论（每条都能用上表复算）

1. **每行节点数是常数**：同一语料 40→160 回合，agent 行中位 152→152（rich）、45→45（short）。
   上一份的结论在富语料下同样成立 —— 长会话变贵 = 行数线性增长 × 单价，不是「每行越来越胖」。
2. **body / chrome 的分界取决于语料，不取决于界面**：单句回复 body=3（占 agent 行 7%），富回复 body=110
   （占 72%）。所以上一份那句「chrome 占 90%」是**单句语料的性质**，不是产品性质；此后以富语料为准。
3. **chrome 是固定的每行税**：42 个节点 / agent 行，单句与富回复**一样多**（42 = 42），与回复多长无关。
   在整个文档里 chrome 占 **34.7%**（9,558 / 27,553）、body 占 **65.9%**。
4. **每回合成本跟节点总量走，不跟回合数走**：同回合数下富语料 2.70× 节点 ⇒ 实测回合 TaskDuration
   1.55×（40 档：129→200 ms）、2.01×（160 档：137→275 ms）。同一语料内 40→160 回合，short +6.2%、
   rich +37.5%。而 RecalcStyleCount / LayoutCount 两档都平（22–28 / 12–14）⇒ **次数不变、每次更贵**，
   与 `83636513` 的定性一致（结构性那一半已在 `0345621f` 拆掉）。
5. **对既有绝对读数的更正**：此前所有「每回合 63.9 ms / 94.2 ms 对 50 ms 预算」都量在 body 占 7% 的语料上
   ⇒ 那些是**下界**。富语料同机 40 档就到 200 ms。绝对预算的判决只能在专用测量机上做；本机 load 9–14、
   swap 用掉 9.9 GB，跨行比较绝对数不成立。

## 四 「哪一半值得动」的判决（带数字）

- **只砍图标**：`svg` + `path` 在 rich 160 档共 4,832 个 = 文档的 17.5%；砍掉一半 = **8.8% 节点**。
  按第 4 条的近似线性关系，换来的每回合成本下降 <10%，而同一份代码在本机不同日子能差两倍以上
  ⇒ **在这个仪器上不可证**，不值得为它删消息操作图标。
- **砍掉全部 chrome**（42/行）：文档 −34.7%，但那等于把复制 / 收藏 / 分支 / 用量整片操作删掉 ——
  这是 UI 变更，不是性能优化，且会撞上「禁止空壳 / 不降级信息量」的规矩。
- **砍 body**：那 66% 就是用户要读的内容（rich 160 档 `td=1,449` 表格单元格、`span=9,012` 语法高亮与行内格式），
  删它等于删功能。
- ⇒ **判决：不做「每行更少 DOM 节点」这一刀。** 它是上一份点名的唯一剩余结构性杠杆，现在有读数支撑的结论是
  「天花板约 9%，代价是删 UI 或删内容」。真正还能动的只有「已沉淀的行不再参与 style recalc」，而那条已经在
  `0345621f` 落到 **3.00 行渲染/回合**（`[budget]` 行的契约下界，40 与 160 档都是 3.00）。

## 五 边界（不许读成更强）

- 富回复是**固定文案、每回合同形**；真实会话的分布（超长表格、多代码块、贴图占位）没有覆盖。本档只把
  「单句语料」这个已知偏差换成了「一段中等复杂度回复」，没有把语料做成分布。
- `TaskDuration` 是**同批次相对对照**，不是预算判决；四档 host load 9.16–14.48 不同，绝对数不可跨行比较。
- 本档**没有改产品代码，也没有声称变快**：`[row-nodes]` 只是把「要不要动 DOM 节点」这个决定从猜测变成读数。
- chrome 的 42 里含 `message-scroller-item` / 分支按钮 / 用量图标等；本档只数了标签分布（`svg=2,095`、
  `path=2,737`、`button=1,936`），**没有**逐个控件给出可删清单 —— 结论只到「哪一半、值不值得」。
