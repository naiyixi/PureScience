# U8：每段事件循环读数 —— **query 与 read 都不阻塞主线程（0/17）**，"同步反序列化"假说被否

- 日期：2026-09-18 / 实例：dev 带窗口 44105 + CDP 9336（真实语料副本）
- 仪器：`resolveVersionContent` 的 reset/read 移到**每个段的两侧**（`queryEventLoopMaxMs` / `readEventLoopMaxMs`），driving 沿用 U6 地图（项目 → `文件` → 等面板行 → 点行 → 断言预览增长）
- 本轮样本：**17 次慢 resolve + 3 次慢 acquire**

## 二、结论（两条，均为实测）

1. **U7 那条"引擎结果在主线程同步反序列化导致阻塞"的假说，不被支持**（0/17）。这两段都是**纯异步等待**：事件循环在整段期间保持健康（0–20 ms 量级），而段本身耗时 21–351 ms。
2. **本轮的 acquire 明显更快**（`resolve 81–86 ms + stat 0–3 ms`，事件循环 0 ms），而 U7 同一条路径是 **220–521 ms**、其中 3 次有 **212 ms** 的主线程阻塞。⇒ **同一路径的耗时在不同运行之间差 3–6 倍**，说明量级更像是**当时的机器/实例状态**（负载、页缓存、磁盘）的属性，而不是代码路径的固定属性。

## 三、因此剩下的是什么（标注为假说，未验证）

`readMs` 在**事件循环健康**的情况下出现 **351 ms（文件仅 21 KB）**，同轮同尺寸文件的 readMs 又是 4–35 ms ⇒ 等待发生在**文件系统侧**，不是应用 CPU。候选机制（未验证）：`/tmp` 副本上的 APFS/FSEvents/Spotlight 行为、硬链接首次触碰、或**本机磁盘竞争**（我这轮同时有 vitest、grep、驱动脚本、以及常驻的 launchd dev 实例在跑）。

**下一步的判据（写死）**：在同一进程内对**同一文件**连续 `readFile` 10 次并打印每次耗时；同时用 `dd`/`time` 直接量同一文件的裸读耗时。若进程内 10 次都在几 ms、而 acquire 里偶发数百 ms，则是**竞争**而非文件本身；若裸读也慢，则是**卷/机器侧**。这一步做完，"acquire 慢"到底该不该由应用来修，才有定论。

## 四、诚实边界

1. 17 样本、单次运行、dev 构建、单语料。
2. 事件循环分辨率为 20 ms，`maxMs=0` 表示窗口内延迟 < 1 ms（取整），不是"未采样"。
3. 本轮 acquire 只有 3 个样本且都不含阻塞 ⇒ **不能**据此说 U7 的 212 ms 阻塞"不存在"，只能说本轮未复现。
4. **未做任何优化。**

## 五、顺手记下的一条环境缺陷（与测量无关）——**已修**

每次重建语料副本时，`rm -rf /tmp/ps-bench-u1` 对从真实根拷来的只读文件报 **Permission denied / Directory not empty**（`claude/skills/**` 等），导致 `/tmp` 里残留旧副本（实测残留 **5,432 项**）。不影响本轮结论（副本每次重新拷入），但清理逻辑会静默失败并累积垃圾。

**修法（已落地并验证）**：清理前先 `chmod -R u+w "$ROOT" 2>/dev/null || true`，再 `rm -rf`。两个启动脚本（`ps-u1-run.sh` / `ps-u1-run2.sh`）均已改；修后用同一残留副本实测 ⇒ **5,432 项全部清除、零报错**。
