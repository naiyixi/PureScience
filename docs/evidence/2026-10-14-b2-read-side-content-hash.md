# B2 第二片：读侧补算内容哈希（记录早于收据的运行也有可复算的哈希）

> 范围：v2.1.0（批 B）第 2 件 **B2「别名级依赖血缘」的第二片**（执行器单元，2026-10-14 凌晨）。
> 第一片（判定引擎 + 界面具名原因）见 `docs/evidence/2026-10-13-b2-alias-lineage.md`；本片只补它具名留下的那一角。

## 一 缺口（来自第一片第六节，逐条具名）

第一片交付了血缘行的其余字段，但 **`producerContentHash` 在当前语料里 1,412 条全是 `not-recorded`**：
哈希取自运行自己的 B1 收据（`riskReview.codeHash`），而收据写入侧当天才落地 ⇒ 语料里 **0/2,197** 条运行带收据。

这使 B2 的计划红线「血缘行 = 产出它的那次运行的**内容哈希** + 别名链 + 变异点，可从运行记录复算」
缺了一角 —— 而缺的正是**本来就可复算**的那一角：产出运行的源文（`script`）就在 run.json 里。

## 二 修法（一处实现在算、三处接线）

| 层   | 落点                                      | 要点                                                                                                                                                                                                       |
| ---- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契约 | `src/shared/notebook.ts`                  | 新 `NotebookRunSourceHash { value, provenance: 'computed-on-read' }`；`NotebookRunRecord.sourceContentHash?`；顺带把既有私有 `isSha256Hex` 导出（读侧唯一的「这是不是内容哈希」定义，避免第二处正则）      |
| 哈希 | `src/main/notebook/run-risk-receipt.ts`   | 新导出 `notebookRunSourceHash(source) = evaluateNotebookRunRisk(source).codeHash` —— **刻意复用收据自己那一次调用**，而不是在新的地方再写一次 `createHash`：配方是公开的，第二处实现就是第二个会漂移的配方 |
| 读侧 | `src/main/notebook/session-read-model.ts` | `toPublicRunRecord()` 在**没有有效收据、且有源文**时附上该字段（`provenance: 'computed-on-read'`），有收据则**不附**（一次运行不留两个哈希）                                                               |
| 判定 | `src/shared/run-alias-lineage.ts`         | `aliasLineageContentHash()` 优先读收据，其次读侧补算值；两者都没有或形态不对 ⇒ `not-recorded`                                                                                                              |

**三条不越线**：

1. **`riskReview` 永不合成** —— 「这次运行没被审过」与「读者事后算了个哈希」是两件不同的事，补算值住在自己的字段里，且带 `provenance` 自陈；
2. **只挂读路径、不落盘** —— `toPublicRunRecord()` 是投影，run.json 里不会出现这个字段（有用例逐字断言盘上文件不含它）；
3. **哈希只在主进程算** —— `src/shared/**` 同时被 node/web 两个 tsconfig 编译，共享层不得引 `node:crypto`（本片把 `node:crypto` 留在主进程的收据模块里）。

## 三 真数据读数（本机真实数据根，只读）

配方：`~/PureScience-DEV/notebooks/<项目>/<会话>/run.json` 逐份读入；按**读侧同一条件**（无有效收据 + 有非空源文）
补算哈希（哈希调用应用自己的 `notebookRunSourceHash`），再把结果喂给第一片的引擎 `computeNotebookStaleReasons`。

| 量                              | 读数                                        |
| ------------------------------- | ------------------------------------------- |
| 数据根里读到的会话 / 运行       | **142 / 2,197**（与第一片同，互为交叉核对） |
| 血缘行                          | **1,412**（与第一片同）                     |
| **其中带真内容哈希**            | **1,412 / 1,412**（修前 **0 / 1,412**）     |
| 语料里带收据的运行              | **0** ⇒ 这 2,197 条全部走补算路径           |
| 应用函数 vs 测试里手算的 sha256 | **2,197 / 2,197 一致，0 不符**              |

**怎么读这个数（诚实口径）**：这 2,197 条哈希是**读侧补算**出来的，因此它证明的是
「补算路径在真数据上逐条等于第三方手算的 sha256」，**不**证明「收据路径在真数据上也跑过」——
后者要等**新运行**经过 B1 写入侧之后才有读数。两半的判据不同，不许混算。

探针本身也按「沉默的零不算读数」写：先断言读到的文档数 > 100、运行数 > 1,000，再断言逐条一致数 == 补算数
（第一版就栽在路径深度写错 ⇒ 0 运行、0 原因，被这两条断言当场拦住）。
