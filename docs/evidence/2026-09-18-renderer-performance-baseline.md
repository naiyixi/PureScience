# 渲染层性能基线（真机窗口 + CDP 采样）

- 日期：2026-09-18
- 实例：`electron-vite dev` **带窗口**实例，**真实数据根**（`~/PureScience-DEV` + `~/.purescience-project`，60 会话）
- 采样方式：Electron `--remote-debugging-port=9333` + Playwright `connectOverCDP`（脚本在 `/tmp/renderer_perf.mjs`，**刻意不放进仓库**：放进仓库会触发 electron-vite 重建，应用重启、CDP 瞬断 —— 这一点踩过一次）
- 原始读数：`/tmp/renderer_perf.json`

## 一、数字

| 指标 | 读数 | 口径 |
|---|---|---|
| 空闲帧间隔（中位） | **16.7 ms** | `requestAnimationFrame` 采样，即稳定 60 fps |
| 空闲最差帧 | 124.4 ms | 1 帧 > 50 ms（1798 帧样本） |
| 空闲长任务（>50 ms） | **0** | `PerformanceObserver { entryTypes: ['longtask'] }` |
| 页面重载 → DOMContentLoaded | 1232 ms | `page.reload` 计时 |
| **搜索面板打开** | **578 ms** | 点入口 → 面板 DOM 出现（DOM 正则匹配，非猜文案） |
| 视图切换 | 803 ms | 其中 **800 ms 是我脚本里写死的等待**，不是应用耗时 —— 这个数**不能当结论** |
| **交互期间长任务** | **4 个 / 最大 524 ms / 合计 742 ms** | 覆盖"开搜索面板 + 切视图"两段 |
| **交互期间最差帧** | **548.4 ms** | 40 帧样本中 5 帧 > 50 ms |

## 二、结论（可支撑的部分）

1. **空闲时渲染层不卡**：60 fps、零长任务。所以"卡"不是持续性的渲染开销。
2. **一交互就出现半秒级冻结**：最大长任务 524 ms、最差帧 548 ms —— 与用户"目前卡、不如对标产品流畅"的主观反馈**方向一致、量级吻合**。

## 三、诚实的负面结果（未证的部分）

1. **"可见可交互"时刻没量到**：我用来判定的文案正则（`New project` / `新建项目`）没匹配上 ⇒ `interactive = -1`。**只有 DOMContentLoaded 的 1232 ms 是可信的**，它**不等于**用户看到内容的时刻。
2. **524 ms 冻结未归因**：采样窗口同时覆盖"开搜索面板"和"切视图"两段，**没有分开**。归因需要分两轮各采一次。
3. **视图切换的 803 ms 无效**：800 ms 是脚本的固定等待。
4. `longtask` 是 Chromium 的粗粒度信号，**不等于**"用户在等"的时长；它只说明主线程被占住了。

## 五、采样流程本身的两次坑（写进流程，而不是靠记性）

1. **窗口可能加载到"不是本次 dev server"的端口**：日志里 vite 在 `5174`，窗口却加载 `5173` ⇒ 页面**空白**（实测 `buttons:0 textLen:0`）—— 那一轮的读数**全部作废**（本档第一节的数字取自 **UI 确实挂载**的那一轮：脚本用 DOM 正则点到了搜索入口、面板也真的出现了，否则会返回 -1）。
2. **Electron 的 CDP 参数会被 electron-vite 的自动重启丢掉**：重启后的 Electron 进程上**没有** `--remote-debugging-port`。

**因此采样流程改为"不满足校验就中止"**：① `ps` 确认 CDP 参数在**活着的** Electron 进程上；② 窗口 URL 的端口必须等于日志里 vite 的真实端口；③ DOM 必须挂载（可点元素 > 0）。该流程已按设计**中止过一次**（`CDP flag on live process: MISSING` → `ABORT`），而不是再产出一组无意义的数字。

## 七、**有效**复测（三项校验全过）

流程修正后再采一次，三项前置校验**全部通过**：CDP 参数在活着的 Electron 进程上 ✓、窗口 URL 的端口 = 日志里 vite 的真实端口（5173）✓、**DOM 真的挂载**（117 个可点元素、正文 28787 字符）✓。

| 场景 | 长任务 | 最差帧 | 帧中位 | 帧数 |
|---|---|---|---|---|
| 空闲对照 | **0** | 17.8 ms | 16.7 ms | 152 |
| **打开搜索面板**（点到"搜索会话和产物…"） | **1 个 / 308 ms** | 323.3 ms | 16.7 ms | 131 |

**可以支撑的结论**：
1. **空闲 60 fps、零长任务** —— 这次是在**真挂载的 UI** 上量的，上一版那份"空闲 60 fps"因此得到**独立复现**；
2. **开搜索面板 = 主线程被占住约 0.31 秒**（单次长任务），人确实会感到"顿一下"。

**不能拿来对比的**：上一版那个 524 ms 是"开搜索面板 + 切视图"**两段合在一起**的桶（308 ms 只含搜索一段）⇒ **不可直接比较**，本档不据此宣布"改进了"。要判定搜索索引吃缓存那一刀的收益，必须**同口径前后对照**（见第八节）。

**一个被证伪的路子**：用普通 Chromium 直接打开渲染页（绕开 Electron 启动参数）**不可行** —— 实测 `window.purescience` 为 `undefined`，页面报 `Cannot read properties of undefined (reading 'lifecycle'/'sessions')` ⇒ 渲染页依赖 Electron 的 preload，浏览器里起不来。
**另一个已知坑**：启动前 `rm -rf out/main out/preload` 会触发重建 → electron-vite 重启 Electron → **CDP 参数丢失**（实测 `MISSING` → 中止）。不删产物、直接启动时，参数稳定在活进程上。

## 九、归因实验结果（UI 口径）：搜索索引的冷读**不是** UI 冻结的主因

同一构建、同一实例内的两条件对照（两项前置校验均通过：页面挂载 117 个可点元素、窗口端口 = vite 端口 5174）：

| 条件 | 长任务 | 最差帧 |
|---|---|---|
| **B：索引冷（刚重启）、不预热目录** | **1 个 / 245 ms** | 262.1 ms |
| **A：先用带 opt-in 的 `load-all` 预热目录缓存，再开面板** | **1 个 / 355 ms** | 358.3 ms |
| （预热调用本身） | — | 2611 ms（首次重请求：冷缓存全量 + 启动协调） |

**读法（不美化）**：预热目录缓存没有带来收益（A 反而略慢）⇒ "半秒冻结 = 搜索索引冷读"这个**UI 层假设不成立**；两次各测 1 次、A 又晚 40 秒 ⇒ 差异只能算噪声。**UI 口径下不能证明任何收益。**

## 九之二、**服务端 A/B：同一改动被证实（省 ~1.18 秒）**

换一个不受 UI/dev/flag 干扰的量法 —— 直接给 `search:query` 的 RPC 计时，两种代码状态各跑一轮（同一语料、同一查询、每次都重启实例）：

| 轮次 | 代码状态 | 首次 `search:query` | 第 2 / 3 次 |
|---|---|---|---|
| **A** | HEAD：索引 `.loadAll({ allowCachedCatalog: true })` | **84 ms** | 62 / 67 ms |
| **B** | **只把那一行改回 `.loadAll()`** | **1260 ms** | 46 / 88 ms |

**结论**：冷索引的**首次**搜索 **1260 ms → 84 ms（省约 1.18 秒）**；两轮的第 2/3 次相当 ⇒ 差值正是那次冷读本身，不是噪声。

**为什么先前 UI 口径测不出来**：UI 那一轮开面板时**并非冷索引**（启动期已有重请求走过目录），所以那 1.18 秒根本没发生在那次交互里 —— 不是改动无效，而是**量法不敏感**。两次结论都保留：**UI 冻结的主因不在索引冷读**（第九节），**而索引冷读本身确实被这一刀省掉**（本节）。

**自证**：B 轮结束后把源码 `cp` 回 HEAD 版本，并以 `git diff --quiet` 断言**无残留改动**（脚本输出「源码已回到 HEAD（无残留改动）」）。

## 十一、**关键修正**：以上数字全来自 dev 构建，会高估开销

对"开搜索面板"那一段做了 CDP CPU 剖析（200 µs 采样，覆盖点击 + 3 秒）：

| 项 | 读数 |
|---|---|
| 采样总量 | 9476 样本 ≈ **1895 ms** |
| 其中 **(idle)** | **1423 ms** |
| 最大 JS 自身耗时 | **`exports.jsxDEV` 151 ms**（`react_jsx-dev-runtime`） |
| 其次 | `jsx` 63 ms · `focus` 34 ms · `getAnimationName`(radix) 29 ms · `(program)` 28 ms |

**关键点**：帧里出现 **`react_jsx-dev-runtime` / `jsxDEV`** ⇒ 这是 **development 构建**。生产构建用编译后的 `jsx`，并去掉整套开发期检查 ⇒ **我此前所有"UI 开销"读数都偏大**，`jsxDEV` 那 151 ms 在生产里**不存在**。

**这解释了归因实验为什么"没有收益"**：那次实验测的是 dev 构建下一个被 dev 开销主导的交互，本来就不该期待缓存那点差别显现出来。

**因此**：以 dev 构建的数字去评测"用户是否感到卡"，**方法上就是错的**。用户感受到的是**打包版**。第七节的 308 ms、第九节的 245/355 ms **一律降级为"dev 构建参考值"**，不得用于宣称，也不得作为优化目标数字。

## 十三、生产构建这条路：发现一个**真缺陷**（已立案），改测打包版

**非打包运行生产产物会硬失败**：`npx electron --remote-debugging-port=9333 out/main/index.js` 起得来、CDP 也应答（**开关必须放在脚本路径之前**，放在后面端点不应答），但 `/json/list` 六轮全是 `[ ]` —— **窗口从未创建**。日志给出真因：

```
at async Object.prepare (out/main/index.js:1462:11)
at async orchestrateAppStartup (out/main/app-startup-*.js:27:21)
at async startElectronApp (out/main/index.js:1358:3) {
  diagnostics: [ { severity: 'error', code: 'builtin.registry-manifest-invalid',
                   message: 'The builtin Specialist registry manifest is invalid.', path: 'manifest.json' } ]
```

`src/main/specialist/builtin-registry.ts:50` 读 `resolveBundledSpecialistsRoot()/manifest.json`，该根走 `process.resourcesPath` ⇒ 直接跑 `out/main/index.js` 时指向 Electron 自带 resources，找不到内置 manifest ⇒ **启动流程抛出并中止**，窗口不创建。

**立案（独立缺陷，不在性能主线里顺手改）**：内置专家 registry 缺失时，启动**整体中止**是过强反应 —— 至少应降级（带诊断启动）或让内置根在"从构建产物运行"时回退到仓库资源目录。修它需要按"改恢复/降级语义前先跑该模块既有测试"的规矩来。

**因此改测打包版**（`/Applications/PureScience.app`，版本 **1.63.0**，就是用户实际体验的那个构建）：为**不碰真实数据**，把 hydration 真正需要的两块**复制**到临时根（会话文档 **60 MB** + `purescience.db` **88 MB**；整根 7.1 GB 不复制），并让打包版通过 `PURESCIENCE_E2E_STORAGE_ROOT` 指向副本；同时用 RPC 核对语料确实加载，并拿到**打包版**的 `load-all` 服务端耗时。

## 十四、**打包版实测：生产环境的 `load-all` 就是 55.4 MB / 1.2 秒**

打包版 1.63.0 对着真语料副本（59 会话）经 web RPC 实测：

| 调用 | 响应 | 耗时 |
|---|---|---|
| #1 | **55,371,532 B（55.4 MB）** | **1566 ms** |
| #2 | 55.4 MB | **1191 ms** |
| #3 | 55.4 MB | **1209 ms** |

**结论（这次是生产数字，不是 dev）**：
1. **55 MB 载荷与 ~1.2 秒服务端耗时在生产构建上同样成立** ⇒ 这不是 dev 开销造成的假象；
2. 因此"把列表路径从 55 MB 里剥出来"（两级目录 + 按需加载）**有明确的靶子**：目标仍是 **响应 < 2 MB、p95 < 150 ms**；
3. 缓存那一刀（`538dd46`/`9e75441`）在**同一路径**上省的是这 1.2 秒里的扫描部分 —— 打包版上未被复测，**暂不作生产宣称**。

**仍未拿到的**：打包版的 **UI 交互数字** —— 打包版启动后**没有打开 CDP 端口**（`ECONNREFUSED 9333`），所以窗口采不到。注意：同一次运行里 **web RPC 是通的**（上表就是它给的），说明主进程活着、只是没开调试端口；且 `ps -p $PID` 报 `alive: no` 属**误判**（macOS 应用包会 re-exec，原 PID 退出）。**下一招**：用 `open -a /Applications/PureScience.app --args --remote-debugging-port=9333` 走 LaunchServices 传参（而不是直接执行内部二进制），或对该 bundle 显式传 `--user-data-dir`。

**主循环里不再纠缠此项**：生产 `load-all` 已足够定靶；UI 数字作为独立事项继续攻。
