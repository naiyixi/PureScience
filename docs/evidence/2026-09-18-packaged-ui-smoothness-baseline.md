# 打包版 UI 流畅度基线 + 一阶归因（v1.64.0，真实窗口）

- 日期：2026-09-18
- 实例：**打包版** `dist/mac-arm64/PureScience.app`（1.64.0），独立端口 44104、独立 `--user-data-dir`、CDP 9335、`runtime/` 硬链
- 语料：真实数据根副本（`/tmp/ps-bench-ui`，59 会话；真实根未被指向）
- 为何必须用打包版：本仓此前的 UI 数字全来自 dev 构建，随后被判定**不可用于宣称**（`react_jsx-dev-runtime` 的 `jsxDEV` 单项 151 ms）
- 三项前置校验（任一不满足即不出数字）：**打包 bundle URL ✓（`app.asar/out/renderer/index.html`）· DOM 已挂载 ✓（119 个可点元素 / 5391 字符）**· CDP 应答 ✓
- 量法：`requestAnimationFrame` 帧间隔 + `PerformanceObserver{longtask}`，每个交互一段独立窗口；归因用 CDP 采样剖析（200 µs，自用时聚合）+ `Debugger.scriptParsed`

## 一、基线（用户感知到的"卡"到底有多大）

| 交互 | 帧中位 | p95 | **最差帧** | >50 ms 帧 | 长任务 | 长任务合计 / 最大 |
|---|---|---|---|---|---|---|
| 空闲 5 s | 16.7 ms | 17.8 | 18.4 ms | **0** | **0** | 0 / 0 |
| 打开搜索面板 | 16.7 | 17.8 | **159.2 ms** | 1 | 1 | **131 ms** / 131 |
| 打开一个会话（读文档 + 渲染转写） | 16.7 | 17.8 | **142.4 ms** | 3 | 3 | **319 ms** / 137 |
| 滚动转写 | 16.6 | 17.9 | 18.4 ms | **0** | **0** | 0 / 0 |
| 打开"文件"面板 | 16.7 | 18.4 | **431.7 ms** | 4 | 1 | **51 ms** / 51 |

**读法（这是本条主线一直缺的数字）**：
1. **空闲与滚动在打包版上是干净的**：稳定 60 fps、零长任务、最差帧 18.4 ms ⇒ "卡"**不是**持续性的渲染吞吐问题，滚大转写这一项也没问题。
2. **卡点是"首次打开某个面"的一次性顿挫**：搜索面板 ~130 ms、开会话 ~319 ms（3 段）、文件面板最差帧 ~432 ms。
3. 之前 dev 构建量到的"搜索面板 308 ms"，在打包版是 **131 ms** ⇒ dev 那批高估约 **2.3×**，与 `jsxDEV` 的判定一致。

## 二、一阶归因（时间花在谁身上）

| 交互 | 采样窗 | **idle** | **busy** | 应用 bundle | **node_modules** | 最大单条 |
|---|---|---|---|---|---|---|
| 打开搜索面板 | 701 ms | 465 | **236** | 23 ms | **0 ms** | `(program)` 167 ms |
| 打开一个会话 | 1086 ms | 590 | **496** | **200 ms** | **0 ms** | `(program)` 213 ms（+GC 32 ms；`Ze` 25 ms、`formatMessageTimestampTitle` 24 ms） |
| 打开"文件"面板 | 941 ms | 626 | **315** | 94 ms | **0 ms** | `(program)` 178 ms（+`getBoundingClientRect` 17 ms） |

**两条被证伪的假设（都是有价值的负面结果）**：

1. **"第三方库慢"——否**：三个交互里 `node_modules` 自用时都是 **0 ms**。
2. **"首次打开时懒加载的分块在编译"——否**：`Debugger.scriptParsed` 实测，搜索面板只解析 **3 个脚本 / 11.7 KB**，开会话与文件面板各 **2 个 / 712 B**，滚动 **0 个** ⇒ 那 167–213 ms 的 `(program)` **不是**新分块的编译。

**因此剩下的解释只能落在**：`(program)` / native 这一桶（其含义本身是"没有归到具体 JS 函数"的样本）+ 等待。当前的观测无法把它们进一步拆开 —— **`(program)` 是一个类别，不是结论**。
**另一个必须一起读的数**：三个交互的 **idle 占 45–66%**（465/590/626 ms）⇒ 墙钟时间有一半以上是在**等**（IPC / 异步），最差帧 431.7 ms 里只有 51 ms 是长任务 —— 那一帧的大部分是**等待**，不是计算。

## 三、下一步（已具备靶子，未做）

| 单元 | 要回答的问题 | 做法 | 判据 |
|---|---|---|---|
| U1 | 三个首次打开路径各自**等什么** | 主进程侧给对应命令计时（`sessions:read-document` / `sessions:list-catalog` / `project-files:*`），按通道出数字 | 每个通道有 ms 与体量；与渲染侧 idle 对齐得上 |
| U2 | `(program)` 里是**解析大载荷**还是**IPC 序列化**还是别的 | 把 2.3 MB 文档 / 0.57 MB 目录的解析单独计时（主进程 + 渲染侧各一次）；必要时用 `Tracing` 替代采样 | 能指名到具体阶段，且改动后最差帧下降 |
| U3 | 文件面板那一帧的 432 ms | 结合 U1（该面板的 IPC 链）+ layout（`getBoundingClientRect` 17 ms 的调用点） | 同 U2 |

## 四、诚实边界

1. **每条交互单次采样**；用途是定基线、杀假设、指方向，不是分布比较（没有前后对照，也不宣称"改进"）。
2. 采样时**用户常驻 dev 实例在跑**（背景负载已计入），渲染进程本身没有别的自动化在跑。
3. **驱动方式是 CDP 真鼠标**，但"墙钟"含我脚本里的固定等待，所以**读 idle 与 long task，不要把 wall 当体验时长**。
4. `(program)` = 未归到具体 JS 函数的样本（含 V8 内部、编译/解析、内建调用等），**本档没有把它拆开**；上面两条被证伪的假设是基于它的两种猜测，均已用独立仪器排除。
5. 未覆盖：Windows/Linux 打包版；大语料（数百会话）下的表现；`⌘K` 与深链等**非鼠标**入口。
