# U12：**第一个真优化** —— 去掉 chip 扇出白付的来源查询（前后实测）

- 日期：2026-09-18 / 实例：dev 带窗口 44105 + CDP 9336（真实语料副本，59 会话 / 50 项目）
- 起因：U11 证实**引擎队列**是共享瓶颈（平凡 `SELECT 1` 与真查询同慢，135 vs 136 ms）。

## 一、改了什么（一处，语义最小）

`HomePage` 的**每项目一次** `listFiles`（limit 30）只为推**文件类型 chip**（`deriveProjectFileKinds` 只读 **`name` + `sortAtMs`**），却要主进程做**两次引擎往返**：页查询 + `fileOriginSession` 来源查询（U2b 实测占单次耗时的 **41%**）。

- `ListProjectFilesRequest` 增加可选 `omitOrigins`（含理由注释）；
- `ProjectFilesQueryOwner.listFiles` 在该标志为真时**跳过来源查询**，`originsMs` 记为 0；其余调用者（文件面板）行为不变；
- `HomePage` 的 chip 调用传 `omitOrigins: true`。
- **未新增 IPC 通道** ⇒ 不牵动通道计数契约（51 通道那批测试零改动）。

## 二、前后实测（同一仪器、同一阈值、同一语料、同一启动阶段）

| 指标 | Before（U2b 同口径） | **After（本轮）** |
|---|---|---|
| `originsMs`（来源查询段） | **29 ms**（中位，占 41%） | **0 ms**（每次样本） |
| `totalMs`（单次 listFiles，中位） | **77 ms** | **51–54 ms** |
| 段构成 | 页查询 47 + 来源 29 | 页查询 **51–53** + 来源 **0** |
| 启动期慢读次数 | 51 | **48** |

**结构性结论**（不受负载波动影响）：每次读取**少一次引擎往返** ⇒ 启动期扇出少发 **≈48 次查询**（约占扇出总查询数的三分之一到一半）。按 U11 的"引擎队列"机制，这既缩短单次调用，也**减轻所有其他查询的排队**。

## 三、真机功能验证（不是只跑测试）

Home 页在真实语料上**照常渲染 18 种文件类型 chip**：`MD / JSON / PY / PNG / CSV / PDF / SDF / GZ / XLSX / NPZ / HTML …`（CDP 读真实 DOM）。
单元层：`HomePage.render.test.tsx` 的 chip 用例已同步钉住新调用形状（`omitOrigins: true`），**865 例全绿**（project-files + pages/home + shared，81 文件）。

## 四、诚实边界

1. 绝对耗时随运行/负载变化（本项目已知），**结构性变化（originsMs 归零、往返数减一）**才是本单元的结论；77 → 51 ms 是**同口径不同负载**下的对照，不作为精确倍数宣称。
2. 只改了 chip 这条路径；**文件面板仍付两次往返**（那里要渲染 Session 归属，不能省）。
3. 扇出本身**仍然存在**（仍是每项目一次调用）—— 下一单元才是"批量化/并发闸"。
4. 未测打包版；dev 构建。
