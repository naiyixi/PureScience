## 0. 开工核对（2026-10-25 实测，纠正下面的旧前提）

- `src/shared/acp.ts:287` 已有 `AcpTurnTokenUsage`（`inputTokens / cacheTokens / cachedReadTokens? /
  cachedWriteTokens? / outputTokens / turnCount?`），随 agent 消息落盘：`session-persistence.ts:170`
  （`turnUsage?: AcpTurnTokenUsage`），读回时经 `sanitizeAcpTurnTokenUsage` 重新校验
  （`session-persistence.ts:1357`），落盘/读回都有用例（`session-persistence.test.ts:631` 起）。
- 它的来源**只有 provider 响应**：`claude-turn-adapter.ts:55`（`response.usage`）、
  `codex-turn-adapter.ts:21,27`（`response.usage` 或 `_meta['purescience/turn-usage']` 的整轮总数）。
  没有任何路径用估算值填 `turnUsage` ⇒ 「`source: 'provider' | 'estimate'`」这个字段在 turn 级
  目前是常量，写进去只是噪声；真正需要区分来源的是 context 级，而那里**已经有**
  `AcpContextUsage.source: 'estimated' | 'native'`（`src/shared/acp.ts:144`）。

因此 §2 第 1、2 条的实质工作改写为：**给现成的 `turnUsage` 补一个「这一轮到底有没有 provider 数」
的判定口径**（拿不到就整条不写，而不是写 0），并把 §2 第 3、4 条（只允许 provider 行进矩阵、日志
与该轮记录对得上）作为验收，而不是新造一个记账结构。

## 1. 现状与缺口

- 已有 `contextUsage`（每轮 prompt/completion/total tokens 的现场估算），但它**不是 provider 的 `usage` 字段**：
  估算与账单可能相差一个数量级，用它算钱就是把猜测写成读数。
- 每个 runtime（claude-code / opencode / codebuddy / codex）都在自己的协议里回 usage；ACP 层目前没有把它
  归一化落盘的地方。
- 检索侧：`openalex` / `arxiv` / `pubmed` 三个源各自有中文术语表行为（见各 descriptor 的 description），
  但没有一份**可复跑的命中率评测**，也没有 `zh_terms` 改写的覆盖率读数。

## 2. 第一步：接 provider usage 记账（必须真实）

1. 在 ACP 事件归一化处（`src/main/acp/*`）抓每个 runtime 的 usage 字段，落到会话的逐轮记录：
   `{ turnId, framework, model, promptTokens, completionTokens, totalTokens, cacheReadTokens?, cacheWriteTokens?, source: 'provider' | 'estimate' }`。
2. **`source` 是这一版的诚实点**：拿不到 provider 字段就落 `estimate`，并在报告里分开统计，绝不混算。
3. 只有 `source: 'provider'` 的行才允许进入后续成本矩阵的 token 列；美元列在接入计费单价表之前**整列不出现**。
4. 自检：同一轮在日志里能对上（`usage` 行 ↔ 会话 JSON 的该轮记录），附一条真机读数。

## 3. 第二步：成本矩阵（token × 墙钟）

- 维度：`framework × model × 题型`（题型取现有 benchmark 集合，先 3 类：文献检索 / 数据计算 / 长文综合）。
- 每个格子记录：`turns`、`promptTokens`、`completionTokens`（**仅 provider 来源**）、`wallClockMs`、失败数。
- 落盘：`docs/bench-runs/<date>-cost-matrix.md` + 原始 JSONL，**必须可复跑**（一条脚本 + 固定 prompt 集）。
- 单价未接入前，报告里明写「本表不含金额，因为计费单价与折扣没有接进产品」。

## 4. 第三步：中文别名检索评测

- 指标 1：中文术语命中率 —— 对一份固定中文术语表（≥40 条，覆盖基因/蛋白/疾病/化合物），三个源各跑一次，
  统计 top-k 命中与所需改写次数。
- 指标 2：`zh_terms` 改写覆盖率 —— 有多少查询在发出去之前发生了改写、改写后命中率是否提升。
- 指标 3：源间差异 —— 同一术语在 openalex / arxiv / pubmed 的命中与排序差异（这三源的术语表行为不同，
  desciptor 里已经写明，评测要把差异量化而不是复述）。
- 落盘同上：`docs/bench-runs/<date>-zh-alias-retrieval.md` + JSONL。

### 4.1 已实现并跑过（2026-10-25）

脚本：`scripts/bench/zh-alias-retrieval.bench.test.ts`（`PURESCIENCE_BENCH_ZH_ALIAS=1`，真实网络，不进 CI）。
40 条术语（基因/蛋白/疾病/化合物 各 10），每条先 `planChineseQuery` 算计划（`unmapped` 空才算可发），
再对三个源各量该源自报命中总数；抽 5 条另发中文原文作对照；失败记成该源该条具名错误。

**两轮读数（同一份术语表）**：

| 轮次 | 被完整改写 | 按名拒绝 | 落盘 |
|---|---|---|---|
| 首轮 | 30/40（**75.0%**） | 10（**其中 9 条是蛋白**，另 1 条「他汀」） | `2026-10-25-zh-alias-retrieval.{jsonl,md}` |
| 补词条后 | 40/40（**100%**） | 0 | 同上（已覆盖） |

补的是 10 条 protein-as-topic 行 + 1 条「他汀类药物」；英文侧逐条从 MeSH lookup 读出，
`scripts/verify-mesh-sources.mjs` 反向核对 **110/110 行与描述符一致**。

跨源差异的一条硬读数：降钙素原**直接发中文**时 `pubmed=0`、`openalex=9926` —— PubMed 吃不下中文这条
在真实服务上复现，OpenAlex 能。这解释了为什么改写是必需的，而不是「更好一点」。

⚠️ 复跑踩过的坑：脚本末尾的 `grep -c "^拒绝"` 在零拒绝时返回退出码 1，看起来像失败；判据要读
`BENCH_EXIT` 与 `Tests passed`，不要读那条 grep 的退出码（与仓里「退出码别经过管道 / grep -c」同一条）。
