## 0. 为什么做这一层

现在的形态是「skill 文档 + 工具名 + 让模型自己写代码」。这恰好是最差的一档：把工具名暴露给模型却不给结构化契约，任务完成率会掉到 baseline 以下；只补文档也只能回收一小部分。真正值钱的是**前置条件 / 产物 / 失败语义**这套机器可读声明——它让 agent 在**执行前**就知道这步能不能跑、缺什么、下一步该跑谁。

对 PureScience 的额外意义：我们的 agent 是四个外部 harness（Claude Code / OpenCode / Codex / CodeBuddy）。契约长在**工具面**上，因此是唯一能跨 runtime 生效的抓手。

## 1. 边界（本版做什么 / 不做什么）

做：
- 契约 schema（requires / produces / prerequisites / aliases / failure_policy）+ 严格解析与校验（错误命名，不静默）。
- 技能侧声明：`SKILL.md` frontmatter 的 `contract` 键（单行 JSON 字符串，避开 YAML 类型强制与嵌套块）。
- 注册表：扫描已装技能目录，聚合契约，出 producer 索引与 agent 可读 manifest。
- 预检：`preflight(capability, observedFacts)` → ready / missing_state / undeclared；**只提示不阻断**（G1：不自动拉起、不静默改道）。
- 首批 7 个技能写真实契约（事实词表见下）。

不做：
- 不改连接器工具调用主链路（U4 再谈，需先有事实来源）。
- 不做 UI（U5）。
- 不给 135 个 connector 工具编造契约：未声明即 `undeclared`，如实标注。
- 不引入失败硬门、不新增命令面（无 catalog/args/composition 计数联动）。

## 2. 事实词表（State Fact）

格式 `<domain>:<entity>[:<qualifier>]`，全小写下划线：

| domain | 语义 | 例 |
|---|---|---|
| `input` | 用户提供的输入物 | `input:expression_matrix`、`input:protein_sequence` |
| `data` | 会话内已算出的数据对象 | `data:matrix:raw_counts`、`data:cluster`、`data:marker_table` |
| `evidence` | 已核验的外部证据 | `evidence:literature_set`、`evidence:verified_reference` |
| `artifact` | 已落盘的产物 | `artifact:figure`、`artifact:table` |
| `prediction` | **模型预测**（≠ 计算结果，G2） | `prediction:structure` |
| `review` | 审查结论 | `review:figure`、`review:citation`、`review:evidence_grade` |
| `claim` | 校准后的论断 | `claim:calibrated` |

关键取舍：**`prediction` 与 `data` 是不同域**。预测结构不得被下游当成已计算结构消费——契约层从词表上就把 G2 的红线钉住。

## 6. 下一步：预检的入口（待拍板，未开工）

预检现在有判定、有事实来源（`factsForSession` 三源），缺的是**一个真入口**。三条可选路，覆盖面与代价不同：

| 选项 | 形态 | 代价 | 判断 |
|---|---|---|---|
| **A. HTTP 路由** `GET /api/v1/capabilities?session=` | 与 `/api/v1/permissions`、`/api/v1/connectors` 同层；headless/CLI 都能用 | 中等：`HeadlessTaskApi` 需拿到 skills 目录与 session 事实；不碰 renderer 的六处计数 | **推荐先做** |
| B. 应用命令（`skills:capabilities`） | 走 `applicationCommandComposition`，桌面与 web 双面同权 | 高：catalog / args / composition / preload / surface-inventory / 命令清单六处计数同批 | 桌面 UI 要展示时再做 |
| C. 只做 CLI 子命令 | `purescience capabilities` | 低，但 CLI 无 TS 依赖，会复制一份解析逻辑 ⇒ 漂移 | 不做（违反"一处口径"） |

A 的验收口径（开工前定好，防止做成空壳）：

1. `GET /api/v1/capabilities` 返回 `{ declared: [...], undeclared: [...], problems: [...] }`，与 `renderManifest()` 同一份数据；
2. `?session=<id>` 时附带该会话的 `facts` 与每条已声明技能的 preflight 结果（ready / missing_state / undeclared）；
3. 无 session 时**不得**猜测事实（返回空 facts 并说明未提供），不能把"没提供"读成"什么都有"；
4. 契约面若必须新增命令，六处计数与 `gen:web-api-map` 同批更新。

### 6.1 拍板：按 A 做（HTTP 路由）

`GET /api/v1/capabilities` 已落地（`src/main/web-service/capabilities-route.ts` + `http-server.ts` 注册），
与 `/api/v1/permissions`、`/api/v1/connectors` 同层，不新增 renderer 命令面，因此**六处计数未动**。

已实现的诚实边界：

- 无 `?session=` → `session: null`，不返回任何"就绪"结论；
- 有会话但拿不到产物库 → `session.status: 'unavailable'` + 具名原因，空事实 ≠ 读不到事实；
- 能读产物时，`notes` 明写 `used_capabilities_not_recorded` 与 `attachments_not_read`——**当前入口看不到
  用户附件与会话跑过哪些技能**，这两条是后续补齐项，不是已覆盖能力；
- 每条已声明技能给出 ready / missing_state / undeclared，缺前置时带 `suggested`（先跑谁）。

## 7. 风险

- **契约漂移**：技能正文改了而契约没改。对策：契约与 skills 同目录、同 commit；全量扫描测试兜底语法，不兜底语义（语义只能靠 review）。
- **词表膨胀**：domain 固定为 7 个，新域需在 `STATE_FACT_DOMAINS` 显式加并有理由。
- **误报阻断**：预检只产生建议，不改变任何执行路径；违反此条即回退。

### 7.5 硬门：应用侧拦截已真机跑通（2026-10-22）

`evidence-grading` 声明了 `failure_policy.missing_state` 且需要 `evidence:literature_set`。
沙盒里以 `PILOT_SKILLS=evidence-grading` 发起一轮（无任何附件），应用的返回：


三件事同时成立：

1. **没有任何模型调用**（`tools: []`，回合根本没开始）；

这条与 7.3 的"讲给模型听"形成对照：同一个契约，作为**建议**时模型无视；

按各自描述里的**真实输入**补，而不是按名字猜：

| 技能 | requires | produces | 说明 |
|---|---|---|---|
| `borzoi` | `input:dna_sequence` | `prediction:regulatory_track` | 从 DNA 序列预测调控谱 |
| `evo2` | `input:dna_sequence` | `data:sequence_embedding` | 基因组基础模型评分/嵌入 |
| `openfold3` | `input:protein_sequence` | `prediction:structure` | 复合物结构预测 |
| `proteinmpnn` | `data:structure_file` | `data:designed_sequence` | 逆折叠需要**骨架结构** |
| `solublempnn` | `data:structure_file` | `data:designed_sequence` | 同上 |
| `scgpt` | `input:expression_matrix` | `data:cell_embedding` | 单细胞表达矩阵 |

真机（`PILOT_SKILLS=proteinmpnn`）：

```
runError: 无法开始「proteinmpnn」：缺少 data:structure_file（structure file），
          可先运行 bionexus-protein-structure-analysis 生成。
          契约声明的处理方式：需要骨架结构文件（PDB/CIF）。先做结构预测或让用户提供结构，再做序列设计。

```

两类前置在信息里被区分开：
- **input 类**（用户才能给）→「当前安装里没有能力声明会生成它，需要用户提供」；
- **派生类**（应用能造）→「可先运行 <生产者> 生成」。

这正是硬门相对"建议"的价值：它给出的是**可执行的下一步**，而且这个下一步来自契约里的
`produces`，不是模型临场编的。

### 7.8 为什么剩下 22 个**不该**补（一次自我否决）

原计划给 bionexus 系列统一声明 `input:research_question`。想清楚后否决了，理由是它会变成误杀机器：

- 研究问题通常写在**消息正文**里，不是附件也不是产物；`factsForSession` 只认附件与产物，
  因此 `input:research_question` 在小节永远"缺失"；
- 一旦给它加 `failure_policy.missing_state`，**每一次选中该技能都会被拦**，包括用户刚刚
  把研究问题打出来的那种情况——这比不拦更糟。

同一条规则也解释了其它不该补的类型：设计/编排/方法论类技能的"前置"是**意图**，
不是可核验的事实。契约只该声明**能被验证的事实**；声明验证不了的，等于给自己造误报。

因此最终覆盖面停在 **29/51**，剩余 22 个保持 `undeclared`（如实标注，不装作有契约）。
若将来要做意图级前置，需要另一套机制（从回合文本抽取意图并让用户确认），不属于本版。

### 7.9 本版小结

- 契约层在**判定路径**上成立：真机三次拦截，理由来自契约，下一步来自 `produces`；
- 在**建议路径**上不成立：工具 0 次调用、10 次运行 0 次读技能、分数无差异；
- 覆盖面 29/51，且刻意不追求 100%——声明验证不了的前置是负债。

### 7.12 机检②：30 条真实失败回放，五类覆盖 100%（2026-10-22）

排期要求「30 条真实失败回放五类覆盖 ≥90%」。落地为三件东西：

| 件 | 位置 |
|---|---|
| 分类器（有序匹配，无匹配返回 `null` 而非硬塞进某一类） | `src/shared/capability-failure-classify.ts` |
| 语料（30 条，每条带出处 `file#L`） | `docs/evidence/capability-failure-corpus.jsonl` |
| 回放测试（含防伪断言） | `src/shared/capability-failure-replay.test.ts` |

真实读数：

```
[failure-replay] n=30 covered=30 rate=100.0%
classes={"invalid_arguments":5,"failed_execution":18,"incompatible_object":1,"unavailable_dependency":6}
```

**防伪设计**：测试逐条读回它声称的出处文件，要求消息**逐字出现**在那里。
一条编造的消息会让测试失败——覆盖率无法通过编造样本抬高。

过程中两处如实处理：

1. 初版 85%（3 条未分类）：两条是我的模式漏了词序（`manifest is invalid`、`Transaction API error`），
   补的是通用词（`is invalid`、`transaction`），不是针对样本的特判；

### 7.18 修复：npm 安装没有 `--registry`（CodeBuddy 装不上的真因）

用户反馈「CodeBuddy 没法下载，下载源有问题」。查证后是这样一个缺口：

```
npm i -g @tencent-ai/codebuddy-code      ← 没有 --registry，只能走 npm 默认源
```

国内默认源（registry.npmjs.org）基本下不动，于是表现为「应用下载不了 CodeBuddy」，
而**用户在应用里无法自救**——没有第二个源可选。

修法（三处一并）：
- `getInstallSpawnSpec` 支持 `--registry`，`runInstall` 透传；
- `runInstallWithFallback` 增加 `registries` 列表：**同一次安装在网络失败后换下一个源重试**
  （不是重试同一个死源），日志写明"X 不可达，改用 Y"；
- CodeBuddy / Codex / OpenCode / Claude(npm 源) 四条安装路径都带上
  `DEFAULT_REGISTRIES`（npmjs → npmmirror）；Claude 的 `managedRegistry: 'npmmirror'` 仍是镜像优先。

测试：`--registry` 出现在命令行；首个源 `ETIMEDOUT` 时自动改用镜像并成功（2 次 spawn，两个不同源）。
