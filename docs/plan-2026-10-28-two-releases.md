## 二 跑项目遇到的问题（真机日志读数）与解决方案

统计窗口：近 7 天 `~/Library/Logs/PureScience/main.log`，**error/warn 共 214 条**。

### 2.1 慢 IPC（141 条，占 66%）——这是「卡」的主要来源

| 通道                         | 次数 | 中位       | 最大        | 方案                                                                     |
| ---------------------------- | ---- | ---------- | ----------- | ------------------------------------------------------------------------ |
| `notebook:state`             | 42   | 112 ms     | **938 ms**  | 状态读取改「增量 + 版本号」，渲染层只在版本变化时重取；写路径节流 100 ms |
| `sessions:save-session`      | 28   | 122 ms     | 541 ms      | 写合并（防抖 150 ms）+ 只写变更字段，避免整份 JSON 序列化                |
| `artifacts:read-preview`     | 11   | 97 ms      | 695 ms      | 预览按需分段读取（前 64 KB 先出，其余滑动加载）                          |
| `settings:list-skills`       | 4    | **662 ms** | **1448 ms** | 复用已有的按目录缓存；IPC 只回 id + 摘要，详情另取                       |
| `reviewer:get-for-session`   | 6    | 513 ms     | 722 ms      | 结果按会话版本缓存，二次读取走缓存                                       |
| `notifications:get-snapshot` | 7    | 425 ms     | 815 ms      | 快照改为增量推送（事件驱动），不再整包拉取                               |
| `compute:jobs:list`          | 5    | 82 ms      | 225 ms      | 与上面同批处理即可                                                       |

**验收**：v2.20.0 发布件连跑 5 次真实会话后统计——上述通道**中位全部 < 80 ms**、无单次 > 400 ms；
`ipc handler was slow` 条数相对本窗口下降 ≥ 80%。

### 2.2 事件循环停顿（24 条，归因全部 `no-cpu-in-process`）

`stalledMs` 读不到（字段口径不一致），且归因只有一个兜底值，等于「测到了但说不清」。
**方案**：把停细分三类——GC（`perf_hooks` 的 GC 观测）、同步 fs、外部 IO；每类落独立字段。
**验收**：停顿记录里**可解释率 100%**（每条都有具体类别与毫秒），不再出现 `no-cpu-in-process` 兜底。

### 2.3 会话/notebook 慢写与「首屏等待」

`session save was slow` 9 条、`notebook state read was slow` 11 条。方案见 2.1。
另加一条**首屏预算**：打开会话 → 消息可见 < 300 ms（本机测量，发布件）。

### 2.4 CI 红不可定因（已解决一半）

日志体积治理 + `ci-failure-digest.mjs` 已落地；**剩余**：把 digest 写进发版前必跑清单。
**验收**：发版脚本输出里必须出现 digest 摘要行。

### 2.5 一处判断失误（流程问题，已记档）

「手动能跑 ≠ 产品在跑同一件东西」：codebuddy 排查中先怀疑 PATH/版本/env，真因是框架→二进制解析。
**方案**：任何「选择 A 却表现像 B」的问题，**第一步打一行 `executablePath`/实际 argv**；已把该诊断行常驻。
