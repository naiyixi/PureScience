# 每轮缺口注入的代价：从 2.9× 到测不出（2026-10-23，v2.16.1 构建上）

## 一句话

v2.16.0 的每轮缺口注入让回合慢了约 2.9 倍；加上「技能目录 mtime 缓存」和「会话→项目记忆」后，
开关打开与关闭**测不出差异**（开启侧还略快，属噪声）。

## 方法

`scripts/bench/latency-probe.sh`：同机、同沙盒根、同模型（deepseek-v4-flash / opencode），
唯一变量 `PURESCIENCE_CAPABILITY_NOTICE`。每侧 3 个「只回复 ok」的回合，计时从
POST `/api/v1/runs` 到该 run 进终态。表里取**中位数**，并记录当时 load。

## 第一轮：缓存前（同一份代码，只有开关不同）

| 侧 | 回合中位 | 注入次数 | load |
|---|---|---|---|
| 关闭 | 13,089 / 13,430（两次原始值） | 0 | 28.0 |
| 开启 | **38,338** | 3 | 25.1 |

约 **2.9 倍**、每轮 +23 秒。代价结构是 O(技能文件数 + 项目数) 的同步 I/O，与回合内容无关。

## 探针自身的 bug（必须记下来）

第一版探针用 `kill -9 $app` 只杀主进程，helper（渲染器/GPU/utility）变孤儿残留。
连跑几次后机器 load 从 19 涨到 54 再到 **138**，得到了一组「开启侧 132 秒」的**假读数**。
已修：`set -m` 让每次启动成为独立进程组 + `kill -9 -- -$app` + 开跑前清理残留。
**被 load 138 污染的那一轮已作废**，不进结论。

## 第二轮：缓存 + 记忆之后

两遍独立测量（交替跑，load 相近时对比）：

| 遍 | 关闭（中位） | 开启（中位） | 注入次数 | load（关/开） |
|---|---|---|---|---|
| A | 12,914 | 11,410 | 0 / 3 | 35.96 / 26.41 |
| B | 12,961 | 10,669 | 0 / 3 | 25.68 / 24.18 |

开启侧与关闭侧的差落在噪声内 → **每轮开销已测不出**。

## 改了什么

1. `SkillCapabilityRegistry` 按**目录 mtime 签名**缓存扫描结果（生产环境；`VITEST` 下禁用，
   否则测试写完 `SKILL.md` 再读会命中旧缓存）；
2. `loadCapabilityFacts` 记住 `sessionId → projectId`，把每轮的 O(项目数) 会话读降到 1 次；
   记录失效时自然回落到全量扫描。

## 因此默认开关怎么定

仍然**默认关闭**——理由不是性能（性能已不是理由），而是它**没有可测的行为收益**
（10 次运行、0 次打开技能文件、分数无差异）。现在的状态是：想开就开，开了不肉疼。

## 前提（别过度解读）

- 机器 load 全程 24–36（Chrome 五个 helper 各 ~80–100%），绝对值整体偏高；
  可推广的是**同一 load 区间内的比值**；
- 每侧只有 3 个回合 × 2 遍，够看出 2.9 倍这种量级的差别，不够支撑 5% 级的判断；
- 启动就绪 4.3–4.5 秒（缓存后），第一轮曾到 29 秒（机器繁忙时），说明冷启动仍受负载支配。
