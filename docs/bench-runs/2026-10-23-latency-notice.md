# 每轮缺口注入的代价（2026-10-23，v2.16.1 构建）

## 为什么量这个

用户报告 v2.16.0「非常卡」。v2.16.0 里我当时新加了**每轮**能力缺口注入：每个回合都要
扫 4 个技能目录（80+ 个 SKILL.md）并遍历所有项目查会话。它是本版唯一新增的「每轮」主进程工作，
所以先量它，再谈别的优化。

## 方法

`scripts/bench/latency-probe.sh`：同一台机器、同一个沙盒根、同一个模型（deepseek-v4-flash /
opencode），唯一变量是 `PURESCIENCE_CAPABILITY_NOTICE` 开关。每侧跑 3 个「只回复 ok」的回合，
计时从 POST `/api/v1/runs` 到该 run 进入终态。

## 读数

| 侧 | 启动就绪 | 三个回合耗时 (ms) | 注入发生次数 | 当时 load |
|---|---|---|---|---|
| 关闭（2.16.1 默认） | 14,481 | 26,017 / 13,089 / 13,430 | 0 | 28.00 |
| 开启 | 16,540 | 38,338 / 39,092 / 36,423 | 3 | 25.11 |

**约每轮 +23 秒**（13s → 37s，三次一致）。这不是抖动，是三倍。

## 必须一起读的前提

- 该机器当时 **load 25–28**（五个 Chrome renderer 各占 ~100%），所以绝对数字整体偏高；
  能推广的是**比值**，不是 13s/37s 这两个数本身；
- 关闭侧第一个回合 26s 明显高于后两个（冷启动 + 首次模型连接），两侧都取后两次更公平：
  13.3s vs 37.9s，仍是约 2.9 倍；
- 因此 v2.16.1 把它默认关闭是**修性能**，不是改设计口味。

## 结论与后续

1. 这个 hook 的代价结构是 O(技能文件数 + 项目数) 的**每轮**同步 I/O，与回合内容无关；
2. 若要重新打开，必须先做缓存（目录 mtime 失效）并把会话查找收敛到当前项目，
   否则它会把每一轮都拖成三倍；
3. 剩下的「卡」不止它：启动就绪 14–16s 本身也偏高，但那是负载下的读数，
   需要在空闲机器上重测才能判断是不是代码问题。
