# 立项：transcript 渲染架构（props → 订阅化 + markdown 结果复用）

> 立项依据：40 回合每回合主线程成本已从 94.2 ms 降到 74.4 ms（回调跳板，commit `4a369a9e`），但
> **80 回合仍有 103.5 ms/回合且随会话长度继续上升**；两次机会主义补丁（收窄渲染窗口、
> `subsequentTurns` 只给 user 行）实测都更差或无效，已 `git checkout --` 还原。
> 结论：剩余斜率不是调参问题，需要一次性把渲染契约改对。

## 一 现状读数（全部可复算，见证据档）

数据来源：`docs/evidence/2026-11-05-perf-baseline-scroll-vs-streaming.md` §六–§二十。

| 口径          | 10 回合 | 40 回合 | 80 回合                |
| ------------- | ------- | ------- | ---------------------- |
| 每回合 task   | 59.9 ms | 74.4 ms | **103.5 ms**           |
| 每回合 script | 34.7 ms | 41.6 ms | **61.0 ms**            |
| 最长单任务    | 0 ms    | 0 ms    | 0 ms（无 >50 ms 任务） |
| 帧 p95        | 19 ms   | 18 ms   | 18 ms                  |

增长斜率 ∝ 行数 ⇒ 一场会话的总成本随长度二次增长。**这就是「越聊越卡」的来源。**

## 二 已排除的假说（不要再试）

| 假说                           | 实测                                                                                                         | 处置     |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------ | -------- |
| 浏览器没跳过屏幕外的行         | `content-visibility:auto` + `contain-intrinsic-size` 早已在沉淀行上（`message-scroller.tsx:79`，有测试断言） | 已排除   |
| 收窄渲染窗口即可省             | padding 60→8：40 回合 74.4→97.3 ms、80 回合 103.5→**199.0 ms**，最长任务 122 ms                              | 已还原   |
| `subsequentTurns` 只给需要的行 | 103.5→102.0 ms，落在噪声内                                                                                   | 已还原   |
| 没有窗口化                     | **有**：`boundedRenderWindow` + 96px 骨架，阈值 150 / padding 60                                             | 前提纠正 |

关键教训：**卸载一行再挂回来的成本，高于让这一行常驻**——因为正文走 `streamdown`，重挂要从头解析
markdown。虚拟化的收益前提是「行便宜」或「重挂不频繁」，当前两条都不成立。

## 三 剩余斜率的机制（探针读数，非推断）

逐槽 props 复用判定失败时按位记录，40 回合：

```
16=3280  canBranchInNewSession      ≈ 2×槽位/回合
 4=1680  revisions                  ≈ 1×槽位/回合
 6=1640  subsequentTurns            ≈ 1×槽位/回合
 0=40    item.message               = 1/回合（稳）
```

**每回合一到，这三项对每一行都换身份 ⇒ 全表重渲一次。** 它们都不是行自己算出来的，是从上层顺着
props 灌下来的；而其中两项（能否分支、后面还有几轮）只在一个极小的交互点上需要。

## 四 不变量（任何阶段都不可破）

1. **流式文字逐增量可见**：不允许为了省成本把增量攒起来再显示（那是拍板项，不在本立项内）。
2. **交互必须用最新上下文**：编辑、分支、修订切换只能打到用户此刻看着的那个会话；禁止用「从依赖里
   拿掉回调」换稳定，必须让引用真正稳定或读 `getState()`。
3. **滚动手感**：粘底、向上翻历史、`scrollToMessage` 定位、run-marks rail 跳转，四项行为不变。
4. **文本必须可查**：`Cmd+F` 命中沉淀很久的消息。
5. **跨行复制**：跨越 3 条以上消息的选区能复制完整文本。
6. **无障碍**：占位骨架不得被读屏当成内容（`aria-hidden`），但真实行必须保持可读。

## 五 设计

### 5.1 P1：三项 props 订阅化（目标：斜率归零）

| 依赖                               | 现状                                                              | 改法                                                                                         | 为什么安全                                                   |
| ---------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `canBranchInNewSession`            | 布尔，`canSendMessage && status==='idle'`，每回合翻转，灌进每一行 | 建 `TranscriptCapabilitiesContext`，**只有那个分支按钮组件订阅**；行 props 不再含布尔        | context 变更只重渲消费者，不重渲祖先行                       |
| `subsequentTurns`                  | 裸数字，新回合 +1，灌进每一行                                     | 从渲染期属性改为**点击时读取**：`countUserTurnsAfter(sessionId, messageId)` 现算             | 值只在确认对话框里用；点击发生在渲染之后，取到的必然是最新值 |
| `revisions` / `revisionNavigation` | map 每回合重建，命中行数组换身份                                  | 改为行内 zustand selector 订阅 `(sessionId, revisionRootId)`，返回稳定引用；无修订的行不订阅 | 选择器返回同一引用时 zustand 不触发重渲                      |

**判据**：探针输出里 16/4/6 **归零或只剩「本回合新出现的行」**；40 与 80 回合的每回合 task 差距
缩到 10% 以内（当前 40→80 是 +39%）。

### 5.2 P2：让重挂变便宜（目标：为 P3 铺路）

先量一件事，再决定做法：**单行重挂到底贵在哪**。用 CDP 剖析一次「窗口抖动」采样，看
`streamdown` 解析、markdown 语法树、React commit 各占多少。

- 若解析占大头 → 在 `AgentMarkdown` 外挂 **LRU（key = 内容哈希 + isAnimating）**，缓存解析产物，
  重挂时直接复用；上限按条数与字符数双限，切会话时不清（同会话内复用价值最高）。
- 若 commit 占大头 → 缓存无效，改走「不卸载」路线：行常驻、仅内部重计算，等于放弃虚拟化。

**判据**：P2 落地后，把窗口 padding 临时调回 8 再测 80 回合，**不得劣于 103.5 ms**；向上翻历史
无白屏、无位置跳动。

### 5.3 P3：窗口策略回归（P2 成功才做）

只有 P2 读数达标，才重新调 `BOUNDED_RENDER_ITEM_THRESHOLD` / `BOUNDED_RENDER_WINDOW_PADDING`，
按 80 回合读数与手验结果取一组值，并且**保留一键回退到 padding 60 的路径**。

## 十三 度量本身有偏差：等待方式影响读数（已修正并复测）

§十二 留下的疑问是「行已经不怎么重渲了，成本还在长」。查剖析时看到一批原生函数——
`isElementHiddenForAria`、`elementText`、`querySelectorAll`、`query`、`normalizeWhiteSpace`——它们不在
我们的 bundle 里（`grep` 出 0 处），是 Blink 内部帧，于是回头查**测量方式本身**。

原来的等待是 `expect.poll(() => page.getByText('Deterministic reply').count())`：**流式期间每 ~100ms 在整篇
文档上重新解析一次文本定位器**。这段工作在渲染进程主线程上，正好落在它等的那段测量区间里，且随会话长度
线性增长——读数的斜率里混进了探针自己的成本。

改法：给助手正文加稳定锚点 `data-slot="assistant-message-body"`，`PERF_WAIT=selector` 时改用
`page.waitForFunction` 只数这个节点（结构比较，不做文本解析），默认模式保留旧行为以便对照。

| 口径                | 文本轮询（旧） | 结构等待（新） |
| ------------------- | -------------- | -------------- |
| 10 回合 每回合 task | 59.9 ms        | **54.3 ms**    |
| 80 回合 每回合 task | 81.2 / 98.0 ms | **71.3 ms**    |
| 10 → 80 增长        | +47%           | **+31%**       |

结论两条，都要写进账：

1. **旧读数里有一部分是探针自己造的**（每回合 5–9 ms，80 回合更多），斜率也被它抬高了；
2. 修正后**增长仍然存在**（54.3 → 71.3 = +31%），所以「越聊越卡」不是纯测量假象——只是幅度比以前小。

## 十四 修正后的增长曲线：80 回合内是平的，160 回合才翻倍

继续追「剩余 +31%」时把**输入方式**也换掉了：perf spec 取输入框与发送键从 `getByRole(...name...)` 改成
CSS 锚点（`data-perf="composer-input"` / `data-perf="composer-send"`）。理由同 §十三——按可访问名定位要遍历
整篇文档算 accessible name，`getTextAlternativeInternal` / `getAriaRole` / `isElementHiddenForAria` /
`checkVisibility` 这批原生帧就是这么来的，规模随行数增长。

用干净量法（结构等待 + CSS 锚点）重测：

| 回合 | 每回合 task  | 每回合 script |
| ---- | ------------ | ------------- |
| 10   | 62.4 ms      | 39.0 ms       |
| 40   | **57.3 ms**  | 35.2 ms       |
| 80   | **63.4 ms**  | 39.3 ms       |
| 160  | **116.7 ms** | 79.3 ms       |

**10 → 80 回合基本持平（57–63 ms，波动 ±5%），到 160 回合才翻倍。** 此前「40 回合 94 ms、80 回合 103 ms、
每回合成本随行数线性增长」的结论，主要由探针自身的定位开销造成，**必须作废**。

### 160 回合是不是渲染窗口造成的？做了判定实验

`BOUNDED_RENDER_ITEM_THRESHOLD` 从 150 临时调到 100000（等于彻底关掉窗口化），同口径跑 160 回合：

| 设置                      | 160 回合 每回合 task |
| ------------------------- | -------------------- |
| 窗口化开启（阈值 150）    | 116.7 ms             |
| 窗口化关闭（阈值 100000） | **106.3 ms**         |

⇒ 窗口化的卸载/重挂约占总量的 9%，**不是主因**；增长的另一部分在别处（160 回合 ≈ 328 条目、两三万像素高的
文档）。实验后已 `git checkout --` 还原，阈值回到 150。

### 现在的诚实结论

1. 「越聊越卡」在 **80 回合以内没有测量证据**；真实拐点在 80–160 回合之间（会话极长的场景）。
2. 前面三项修复的收益是真实的（沉淀行渲染次数 226 → 2，`commitHostUpdate` 559 → 81 ms），但**它们降低的是
   常数，不是随长度增长的斜率**——斜率此前被我自己的探针放大了。
3. 160 回合那一档需要单独剖析（下一次用 `PERF_TURNS=160 PERF_WAIT=selector` 跑 profile），在此之前不再声称
   任何与长度相关的结论。

## 十五 长会话的 DOM 事实：优化在用，但文档本身已经很高

新增非门禁诊断 `e2e/perf/content-visibility.spec.ts`（`PERF_TURNS=120 npx playwright test …`），
在 120 回合的真实会话里读 DOM 事实，而不是猜：

```
turns=120  bodies=120  domNodes=7560
nodesWithContentVisibilityAuto=240      ← 沉淀行确实带 content-visibility: auto
流式行                          cv:visible（预期的例外）
正文容器高度                    24,035 px（视口 819 px）
单行最高                        124 px
```

祖先链（自下而上）：`assistant-message-body` → … → `div[data-slot=message-scroller-item]{cv:auto,h:80}` →
`div[data-slot=message-scroller-item]{cv:visible,h:124}` → 内容容器 `h:24035` → scroller。

三条事实：

1. **`content-visibility: auto` 是生效的**（240/480 个 item 节点带 auto），不是「优化没写上」；
2. 渲染窗口也在生效（150 阈值那一侧），但 §十四 的实验已经说明它**净成本是正的 9%** —— 因为卸载/重挂
   比常驻更贵（`streamdown` 要重新解析整段 markdown）；
3. 文档高度 **24,035 px / 819 px 视口 = 29 屏**，7560 个 DOM 节点。160 回合那 23 ms/回合的 `(program)`
   就是在这种体量下的样式重算与布局维护，`content-visibility` 只能跳掉离屏行的**绘制**，跳不掉容器层面的
   布局账。

所以「让重挂变便宜」不是可选项，是让窗口化转为净收益的前提：先给 markdown 结果做内容哈希缓存，重挂时复用
已解析结果，窗口化才能把常驻节点从 240 降下来而不付解析代价。这是 P2，仍未开工。

## 十六 P2 预演：两个负结果，以及为什么它吃不下那 +85%

用户批准做 P2（让重挂变便宜）后，先做两件成本最低的事来确认方向，两件都是负结果。

### 负结果一：`useDeferredValue` 反而更慢（已还原）

给流式行加 `useDeferredValue(content)`，想让 React 跳过中间帧只渲染最新内容。160 回合：

| 口径          | 基线     | `useDeferredValue`      |
| ------------- | -------- | ----------------------- |
| 每回合 task   | 116.7 ms | **148.9 ms**            |
| 每回合 script | 79.3 ms  | **100.8 ms**            |
| 最长任务      | —        | 164 ms（36/36 超 50ms） |

原因被现有护栏当场抓住：`ConversationPanel.transcript-render.test.tsx` 与
`WorkspaceMessageScroller.interaction.test.tsx` 报 markdown 渲染从 `['partial more']` 变成
`['partial', 'partial more']` —— 延迟值先渲染旧内容、再补一次新内容，**同一段 markdown 被解析两遍**。
护栏在它上线前就拦下了。已 `git checkout` 还原，两测回归 1915 passed。

### 负结果二：本来就没有「一帧多个 chunk」可合并

合并流式增量（每帧只提交一次）是另一个思路，但真实读数直接否掉了前提：

```
160 回合：mutation batches ≈ 1340 commits over frames = 1625 | per frame: 0.82
```

**每帧不到一次提交** —— chunk 到达率本来就低于帧率，没有可合并的中间量。这条路不成立，没有实施。

### 所以 P2 的天花板在哪里

- §十四 的判定实验：关掉窗口化 160 回合从 116.7 降到 106.3，说明**窗口化本身的净成本只有 9%**；
- 也就是说，哪怕 markdown 解析缓存做到完美、重挂零成本，**最多只能拿回这 9%**；
- 剩下的增长在 `(program)`（布局/绘制，23 ms/回合）与 React 提交链，靠「重挂变便宜」碰不到。

要让窗口化真正吃到收益，得同时把窗口收窄到远低于当前 150 条目、并让重挂为零成本——而重挂成本的大头是
`streamdown` 的解析流水线，它没有对外暴露「解析产物」这一层（`Block` 内部直接调用 react-markdown 渲染），
缓存要么改调用链更上方的 API（`streamdown` 没有暴露解析产物这一层），要么在我们这边重写整条 remark/rehype 流水线。后者是高风险的等义改写，无法在短期验证。

**结论：P2 的性价比不成立，暂不实施。** 维持现状（content-visibility + 150 条目窗口）是当前证据下的最优解；
160 回合那一档的剩余成本属于「超长文档的布局账」，要动就得动 markdown 流水线本身，那是另一个量级的立项。

## 十七 P1-c 已落地：`revisions` 按内容而不是按数组身份进缓存键

`revisionsByRootMessageId` 在 `activeSession.conversationGraph` 每次变化时都会重算，流式期间每 chunk 一次；
`groupRevisionsByRoot` 只对**内容逐项相同**的桶复用数组身份，而调用链更上方重建后元素引用并不保证相等，于是桶数组
频繁换身份，`propsDeps` 里的 `revisions`（位 4）每回合漂移 42 次。

改法：行的缓存键改成 revisions 的**内容签名**（`id:introducedOnBranchId` 拼接），数组换身份但内容没变时
不再让缓存失效。

读数（确定性计数器，不受负载噪声影响）：

| 口径                  | P1-b                | P1-c                |
| --------------------- | ------------------- | ------------------- |
| props 漂移（40 回合） | `4=1680 0=40 2=40`  | **`0=40 2=40`**     |
| 渲染计数（40 回合）   | total 2288 median 2 | total 2406 median 4 |

位 4 与位 6 都已归零，只剩「本位消息对象」（40 = 1/回合，流式消息本身）与 `artifacts`（40）——
这两项是每回合真正变化的数据，属于合理重渲。

### 160 回合的 wall-clock 现在测不出差异了

同一份构建连跑三次：**130.4 / 124.3 / 156.4 ms/回合**（script 88.6 / 84.2 / 105.3）。基线那一轮是 116.7。
**抖动 ±25%，已经大于任何单次改动的预期收益**，所以这一档不能再用单次读数判定好坏——既不声称 P1-c
带来了 wall-clock 改善，也不声称它变慢。要在这一档下结论，必须改成多次取中位数，这是后续任何 160 回合
实验的前置条件。

## 十八 度量环境本身不干净：这台机器在跑别的重活

上一节说「160 回合单次读数不再有分辨力」，于是加了 `scripts/perf/measure-median.mjs`：同一份构建连跑 N 次
取中位数并报spread。第一次用它跑 5 次 160 回合：

```
run 1–5 task = 247.4 / 162.5 / 171.3 / 162.5 / 208.2 ms
task   median=189.1ms  min=162.5  max=247.4
script median=126.3ms
spread=44.9% of median
```

**五点中位数 189 ms，比先前单次 116.7 ms 高 62%，spread 44.9%。** 查原因不是代码：

```
load average: 7.44  15.42  16.90
CPU: PureScience.app 42% · SkyLight 42% · Hermes 桌面 25%+20% · PureScience 渲染进程 19%
```

机器上同时跑着用户自己的 PureScience 应用、Hermes 桌面、还有别的进程，**负载长期在 7–17**。结论：

1. 这台机器上的**绝对**性能读数只在同一批、同一负载带内可比；跨批次比较（比如今天的 116 vs 明天的 189）
   没有意义；
2. 只有**同批次内的相对比较**（例如同一后台进程里依次跑 40 / 80 / 160 回合）才成立——先前那条
   「80 回合持平、160 回合翻倍」的曲线正是同一批次内测的，所以它仍然有效；
3. 度量脚本现在会在开始和结束时打印 load average，并在 load > 4 时明确警告「这些数字只对本批次有效」。

要把 160 回合这一档做成可跨天比较的指标，得先解决环境：要么在这台机器上单独占测量（关掉其它应用），
要么把 perf 基线搬到 CI 的专用 runner 上。在解决之前，我不会再用 160 回合的绝对读数下任何结论。

## 十九 四个交互场景的场景基线（附负载带，只能同批次比较）

`PERF_WAIT=selector npx playwright test e2e/perf/smoothness.spec.ts` 一次跑完流式、输入、滚动、命令面板、
重开重会话五个场景。本次读数（**宿主 load 6.98 / 10.38 / 14.14，属高负载带**）：

```
instrument: usable — idle cadence 17ms ≥50fps（仪器自证通过，说明测量机制本身有效）
streaming  10 turns  每回合 task 128.8 ms · script 68.0 ms · frames=201 · p95=32ms
typing              longest=77ms · 1/1 超 50ms · frames=108 · p95=33ms
scrolling           p50=18ms/帧 共 240 帧 · longest=0ms · 0 个超 50ms · mutation 0.00/帧
command palette     105ms 到可见 · longest=71ms（6 帧，样本不足 20 不取 p95）
reopen heavy session 145ms 到可见 · longest=0ms
ipc project.list    p50=0ms p95=1–3ms max=5ms
```

两条可直接用的结论：

1. **滚动是干净的**：240 帧 p50=18ms、零长任务、零 mutation —— 滚动路径没有可改的东西；
2. **流式 10 回合这次是 128.8 ms，而低负载时同 spec 是 62.4 ms** —— 同一份代码、同一个 spec，**环境差异 2 倍**。
   这就是为什么这一节的数字只能和同一批次的其它数字比，不能和 §十四 那批比。

命令面板 105ms 与重开重会话 145ms 是目前唯一两个"用户会直接感知"的绝对值，都发生在高负载带，需要在
干净环境下复测才能定性。

## 二十 P2 的死亡证明：markdown 解析量不随会话长度增长

给 `RichAgentMarkdown` 加了独立的解析计数器（`countMarkdownRender`，与行渲染分开），因为「行重渲」和
「markdown 重新解析」是两件事：组件按内容 memo，行渲染 10 次也可能只解析 1 次。这是确定性计数，
不受宿主负载影响。

| 回合 | 行数 | 行渲染 total      | 行渲染 median | markdown 解析       | 解析字符          |
| ---- | ---- | ----------------- | ------------- | ------------------- | ----------------- |
| 40   | 81   | 4158（104/回合）  | 4             | **80（2.0/回合）**  | 4560（114/回合）  |
| 160  | 321  | 53419（334/回合） | 2             | **320（2.0/回合）** | 18240（114/回合） |

**markdown 解析：40 回合与 160 回合都是每回合 2 次、114 字符，完全没有增长。**

于是 P2（markdown 解析缓存）的前提——「重挂要重新解析整段 markdown，所以窗口化很贵」——**不成立**：真实
数据里根本没有发生随长度增长的重新解析。§十四 里窗口化的那 9% 成本不是解析造成的，§十六 里「P2 天花板
9%」的推断也随之作废。P2 到此关闭，不再讨论。

### 留下的真问题：行渲染次数随会话增长（104 → 334/回合）

行渲染 total 的增长几乎全部来自**流式中的那一行**（median=2 说明绝大多数沉淀行整场只渲染 2 次，
max=671 说明个别行被反复渲染）。160 回合时单行每回合约 334 次，40 回合时约 104 次。

这有两种可能，还没有区分开：① 长会话里 chunk 到达更密（假 agent 在不同负载下投递速率不同）；
② 每次 chunk 触发行渲染不止一次。**下一步必须先把「每回合 chunk 数」也计出来做归一化**，否则
「334 次/回合」这个数字本身就可能是把 chunk 数量误当成开销。

## 二十一 归一化后的真相：每回合只有 1 个 chunk，流式那一行却被渲染几十到几百次

上节要求「先数出每回合 chunk 数」。加了 `countStreamChunk`（在 store 的 `appendAgentMessageChunk` 入口计数）
和一个 `__scroller__` 桶（数容器自身渲染次数），20 回合读数：

```
chunks            20 total（1.0/回合），committed=20
行渲染            41 行 / 956 次（47.8/回合），median 4，max 88
scroller 渲染     223 次（11.2/回合）
markdown 解析     2/回合（与长度无关，见 §二十）
```

三条结论：

1. **每回合只有 1 个 chunk**。所以「334 次渲染/回合」不是 chunk 多，而是同一个 chunk 之后发生了大量与文本无关的重渲；
2. **容器每回合渲染 11 次**，说明每回合有约 11 次对话状态提交（活动/状态/用量等），远多于 1 次文本增量；
3. **流式那一行被渲染约 44 次/chunk（20 回合）**，而 160 回合时是约 334 次/chunk —— **同一件事，长了 7.6 倍**。

也就是说：问题不是「chunk 越多越卡」，而是**同样的状态提交次数下，长会话里流式行被渲染的次数成倍增加**。
这正好解释了为什么 160 回合的 `(program)` 与 React 提交链成本会翻倍，而行渲染中位数却一直是 2。

### 下一步（明确、可执行）

需要数「每次状态提交渲染了多少行」，而不是总数。做法：把行渲染计数按 `commitId` 分组——每次 store 更新自增
一个 id，行渲染时把这个 id 记进去，就能得到「一次提交 → N 行」的分布。如果长会话里 N 随行数增长，说明有某个
未被 memo 住的路径把整表带进来了（尽管 median=2 看起来不像）；如果 N 恒定而提交次数增长，那问题在事件层。

## 二十二 渲染原因分桶：53,024 次渲染里没有一次是「文本变了」

上节怀疑「长会话里流式行被渲染更多次」。加了 `recordRenderReason`（按行比较上一次渲染的 content / status），
把每次渲染归到 first / content / status / other 四个桶，20 与 160 回合同时测：

| 回合 | 总渲染 | first | content | status | other     | scroller | chunks        |
| ---- | ------ | ----- | ------- | ------ | --------- | -------- | ------------- |
| 20   | 1010   | 40    | **0**   | 20     | **950**   | 213      | 20（1/回合）  |
| 160  | 53504  | 320   | **0**   | 160    | **53024** | 1849     | 160（1/回合） |

**`content=0`——全场没有一次渲染携带了新的文本。** 也就是说：

1. 假 agent 每回合只投递 1 个 chunk，且**整段文本一次到达**，所以「流式」在这个场景里根本不产生逐字更新；
2. 53,024 次重渲中，**99.1% 既没有新文本也没有状态变化**（`other`），它们是被别的什么东西触发的；
3. 这些 `other` 渲染集中在**当前那一行**（321 行里 median=2，max=698）。160 回合每回合约 330 次，
   而每回合墙钟只有约 130ms —— **相当于每 0.4ms 一次渲染**。0.4ms 不是定时器的节奏，是同步级联的节奏。

### 这改变了前面的判断

- §二十一 说「44 / 334 次渲染每 chunk」——**准确说法是「每 chunk 只有 1 次文本渲染，其余 330 次与文本无关」**；
- 所以「减少 chunk 数量」「缓存 markdown」都不可能碰到这块成本（再次印证 §二十、§十六 的关闭决定）；
- 真正要找的是**什么东西在同一个 turn 内把这一行重渲了 330 次**，而它只在长会话里放大（20 回合是 47 次/回合）。

### 下一步：给 store 提交打标

现在缺的是「谁触发的」。做法：每次 `session-store` 写入自增一个 commitId，`useSessionStore` 的选择器命中时把
commitId 记进行的渲染原因里，得到「一次提交 → 多少行渲染」以及「这一行的 330 次渲染分别由哪些提交触发」。
这能一次性区分：某处 setState 级联 / 某个订阅被高频通知 / 某个 effect 在长文档里反复收敛。

## 二十三 「同步级联」的判断被证伪：每次提交都会重渲约 6% 的行

上节我写「0.4ms 一次的节奏是同步级联」。给 `session-store` 的每次写入打 commitId、并让行渲染记录当前
commitId 之后，这个推断**被直接证伪**：

| 回合 | 提交次数          | 行渲染 | **每次提交渲染的行数** | 最大    | 无新提交的渲染 |
| ---- | ----------------- | ------ | ---------------------- | ------- | -------------- |
| 20   | 435（21.8/回合）  | 1181   | **2.71**               | 22      | **0**          |
| 160  | 2707（16.9/回合） | 51185  | **18.90**              | **162** | **0**          |

1. **`renders with no new commit: 0`** —— 每一次行渲染前面都有一次 store 写入，**没有本地状态级联，也没有孤儿渲染**。
   我上节说的「0.4ms 同步级联」不成立，作废；
2. **真正的缺陷在别处：一次 store 写入会重渲的行数随会话变长而线性增长**（2.71 → 18.90，7 倍）；
3. 换算一下比例：20 回合 2.71/41 行 = **6.6%**，160 回合 18.90/321 行 = **5.9%** —— **每次提交固定重渲约 6% 的行**。

6% 这个稳定比例说明它不是「最新那几行」的问题（那样应该是常数），而是**某个随行数扩张的窗口**：每多 100 行，
每次提交就多渲 6 行。这也解释了为什么 160 回合每回合 320 次渲染而 20 回合只有 59 次：不是提交变多（反而变少，
21.8→16.9），是**每次提交摊到的行变多**。

### 这是整条性能线的真正靶心

- 与 chunk 无关（每回合 1 个）、与 markdown 解析无关（2 次/回合恒定）、与本地级联无关（0 次孤儿渲染）；
- 只要「每次提交重渲的行数」能压回常数，160 回合的行渲染就会从 320/回合 掉到与 20 回合同级；
- 下一步：在 `recordRenderAtCommit` 里记录**每次提交渲染了哪些行 id**，看这 6% 是「连续一段」还是「散落」，
  再决定是按身份缓存修，还是按窗口边界修。

## 二十四 形状：不是连续窗口，是尾部一片区域里散落重渲

`bumpStoreCommit` 现在保留最近 60 次提交各自渲染过的行 id，spec 用 DOM 里的 `data-message-id` 顺序把 id 换成
下标，再看每次提交命中的行是「连成一段」还是「散落」。20 回合（41 行）：

```
commits 466（23.3/回合） 每次提交 2.86 行（max 22）
[commit-shape] sampled=15  contiguous=0
               rows avg=20.1  span avg=77.1  distanceFromLastRow avg=5.9
```

三条结论：

1. **`contiguous=0`**：15 次「渲染了 ≥2 行」的提交里，**没有一次是连续的一段**。所以不是「跨窗口边界」那种整块重挂；
2. **命中行平均 20.1 行、散布在平均 77 行的范围内**（下标按 DOM 顺序，含修订分支副本，所以跨度大于行数）；
3. **离最后一行平均 5.9 行**：重渲集中在**尾部区域**，往外递减。

也就是说：每次 store 写入，会让尾部一片区域里约 20 行的 memo 键同时失效，而这些行彼此不相邻。这与
「分组 / 相邻关系 / 修订归并」这类**依赖邻居**的 props 一致——只要尾部有任何变化，这些行的分组标识就重新计算。

### 160 回合这次没跑出来

同一条命令在 160 回合档**超时失败**：`page.waitForFunction: Timeout 60000ms exceeded`（等待下一条回复出现）。
两种可能没有区分开：① 宿主负载导致单回合卡顿超过 60 秒；② 长会话里真的出现了超过 60 秒的停顿（那就是用户说的"卡"）。
按本项目规矩，这一档记为**证据不足**，不作为结论，也不据此改代码；下次重跑时把该等待上限调到 120 秒并记录实际耗时。

## 二十五 三个否定：不是重挂、不是 props、不是订阅值变化——成本压在助手行上

在 §二十四 的基础上又加了三个计数器：行挂载次数（`useState` 惰性初始化里计一次）、store 选择器被调用/命中次数、
按行渲染次数排序的热行表。40 回合读数：

```
commits        684（17.1/回合）  每次提交 5.25 行（max 42）
mounts         80（2.0/回合）    行数 81  renders/mount = 49.65
selector       calls 31,774（794/回合）changes 82（2.05/回合）ratio = 0.003
hot-rows       message-…-1=180  …-3=180  …-5=174  …-7=166  …-9=160
```

四条结论，三条是否定：

1. **不是重挂**：81 行只挂载了 80 次（每行一次），`rendersPerMount=49.65` 说明是同一个组件实例反复渲染；
2. **不是 props**：把 memo 比较器临时改成「只有 message 身份或编辑可用性变化才渲染」，每次提交的行数从
   5.08 只降到 4.83（−5%），说明渲染**根本不走 props 这条路**；
3. **不是订阅值变化**：选择器每回合被调用 794 次（每个提交都扫全部行），但真正变化的只有 **2.05 次/回合**
   （`ratio=0.003`）。zustand 不会因为「值没变」而重渲；
4. **成本集中在助手行**：热行 id 全部是 `message-<时间戳>-<奇数>`，即**每个回合的助手行**，每行约 160–180 次渲染，
   换算下来每个助手行在每个后续回合要重渲约 4.5 次。

## 这排除了 Memo 与缓存方向

前几轮我一直在缓存和 memo 上找原因（P1 三项、P2、窗口化），现在有确定读数：**这些行的重渲既不走 props，
也不走订阅值**。剩下的机制只有两个——行内部自己的 state/effect，或**行内某个子组件的 setState 被 React
记在了这一行的渲染预算上**（例如活动分组把状态放在了行内）。

## 下一步

在助手行内部做二分：先给「活动分组 / 用量 / 复制按钮」三块各自的订阅计数，哪一块每回合触发 4~5 次，就是它。
这次不要再从 props/memo 角度猜了。

## 二十六 计数器自身出了问题：每条消息在 DOM 里出现两次

上一节把原因指向 `canEditMessage`（`edit=3986`）。为了验证，我给编辑可用性 Provider 加了独立计数：
Provider 自己只翻转 **200 次**（40 回合，约 5 次/回合），而行级计数报告 `edit` 变化了 **3,973 次**。两者差 20 倍，
说明**行级计数把两个不同的渲染路径混在同一个 key 里**。

于是查 DOM：

```
[dom] message-ids=164  unique=82  scroller-items=164  counted-rows=81
```

**每条消息在 DOM 里出现了两次**（164 个 scroller item / 82 个唯一 id），而实际渲染计数只有 81 行。这也解释了
更早的两个异常：§二十四 里 `span(157) > rowsInDom(81)`、以及 `edit` 值在两个副本之间来回跳。

### 这条结论要先自证，再据此改代码

- 现在**不能**说「重复渲染是性能问题」——需要先确认第二个副本是什么：占位行（只为撑高度）还是真的把整行渲染了两次；
- 也不能再用按 `message.id` 聚合的计数器下任何结论，因为它们把两条路径加在一起；
- 下一步：把计数器改成按 `(surface, id)` 记，并在两个副本上加不同的 `data-surface` 标记，再看每个提交在每条路径上各渲染几行。

**这一节的诚实结论**：性能问题的定位在本轮后退了一步——不是发现新缺陷，而是发现**先前那条「成本压在助手行」
的证据被重复 DOM 污染了**，必须重新测。§二十五 的三条否定（不是重挂、不是 props、不是订阅值）仍然成立，
因为它们各自有独立证据（挂载数、比较器实验、selector 命中率）。

## 二十七 作废「成本在助手行」：98% 的渲染发生在**用户行**

按角色分桶后一刀切开（40 回合）：

```
[roles]  totals={user:3364, agent:80}  changes={user:3323, agent:40}
[causes] first=81  edit=3323  status=40
[edit-flips] Provider renders=435  flips=173
[dom]    message-ids=164  unique=82  scroller-items=164  counted-rows=81
```

1. **§二十五 的「成本压在助手行」作废**。那一节我是按 id 前缀 `-1/-3/-5` 猜的奇偶，猜错了。
   真实分布：**用户行 3,364 次渲染，助手行只有 80 次**（每行一次）。用户行占 **98%**。
2. 用户行走 `EditableWorkspaceMessageItem` → 订阅编辑可用性 context → 每次渲染把 `canEditMessage` 传进 memo 的行组件。
   这解释了为什么上一轮把 memo 比较器收窄（只看 message 身份 + 编辑可用性）没有效果——**编辑可用性正是那个在变的东西**。
3. **但这里还有一个没解释的矛盾**：行级计数说 `edit`（`canEditMessage`）在一次渲染到下一次之间变了 **3,323 次**，
   而 Provider 自己的值只翻转 **173 次**。两者差 19 倍，用现有计数器无法说明。

## 手搓计数器到这里为止

这一轮的四次来回里，我有两次得到的是**误导信号**（先"助手行"，再"edit 变了 4000 次"），每次都要再花一轮去证伪。
原因很清楚：按 `message.id` 聚合的计数器分不清「同一条消息被两条路径渲染」和「同一个实例反复渲染」，而 DOM 里
每条消息确实存在两个 item（164 个 item / 82 个唯一 id）。

**下一步换仪器**，不再手搓计数：用 React 自身的渲染归属（`why-did-you-render` 或对 `beginWork` 打点）直接问
「这次渲染是哪个 prop/context 变化的」，一次就能给出答案，而不是靠我在这三条曲线之间猜因果。

### 已经坐实的结论（不依赖上述矛盾）

- 用户行承载 98% 的行渲染（3,364 vs 80，按角色直接统计，不受 id 重复影响）；
- 用户行唯一的可变输入是编辑可用性 context（`EditableWorkspaceMessageItem` 只订阅它）；
- 该 context 的 Provider 值在 40 回合内只翻转 173 次，远小于行渲染次数；
- 因此**只要让用户行不再依赖这个 context 的每次提交**（例如把编辑入口改成悬停/聚焦时才订阅，或把可用性
  以 ref + 事件形式下发），就有明确收益路径——这条不依赖解开上面的矛盾，可以先做。

## 二十八 修复：编辑可用性不再广播到每一行（行渲染降 99%）

### 改了什么

原来 `EditableWorkspaceMessageItem` 在每个用户行里订阅编辑可用性 context，并把 `canEditMessage` 作为 prop
传给行组件。这个 context 每个回合翻转 3~~5 次，**每次翻转都会把所有用户行重渲一遍**——这就是「一次提交重渲
5~~6 行、且随会话变长」的真正来源（行数越多，单次广播越贵）。

改成：

1. 上下文值额外镜像到模块变量（`setWorkspaceMessageCanEdit` / `readWorkspaceMessageCanEdit`），提交编辑时
   在**点击那一刻**读取，不再依赖渲染期 prop；
2. 只有真正需要响应的四个控件（编辑按钮、编辑态发送按钮、上/下一个修订）用 `EditAvailability` 边界单独订阅
   context，行本身不再订阅；
3. 删掉 `EditableWorkspaceMessageItem` 包层与 `canEditMessage` prop（`WorkspaceMessageItem` 现在用户行、
   助手行走同一条渲染路径）。

### 确定性计数（不受宿主负载影响）

| 档位     | 指标             | 改前          | 改后     | 变化       |
| -------- | ---------------- | ------------- | -------- | ---------- |
| 40 回合  | 行渲染总数       | 3,926 ~ 4,907 | **120**  | −97%       |
| 40 回合  | 中位渲染/行      | 2 ~ 4         | **1**    | —          |
| 40 回合  | 单行最多渲染     | 194 ~ 223     | **2**    | −99%       |
| 40 回合  | 每次提交渲染行数 | 4.83 ~ 5.67   | **0.17** | −97%       |
| 160 回合 | 行渲染总数       | 52,674        | **479**  | **−99.1%** |
| 160 回合 | 每次提交渲染行数 | 18.90         | **0.17** | **−99.1%** |

关键：改前 160 回合是 52,674 次、改后 479 次，而**提交次数没变**（2,707 → 2,795）。也就是说「随会话变长」的
那个放大器被拆掉了，不再是「每次提交渲染 6% 的行」，而是**每次提交最多渲染 1 行**（`max=1`）。

### 功能没有被改坏

- `e2e/workspace-conversation.spec.ts`（编辑消息 → 修订持久化 → 重开仍在）：**3 passed**；
- 全量 unit：**1,464 files / 18,325 passed / 227 skipped / 0 failed**；
- `typecheck:web` 0 error；`eslint` 0 error。

### 墙钟时间这一轮不作结论

同批次读数（40 回合 task 149.1 / script 81.1 ms；160 回合 226.7 / 140.4 ms）与历史干净口径（57.3 / 116.7）
**跨批次不可比**（宿主 load 长期 7–17）。能说的只有同一批次内的斜率变化：160/40 的 task 比值从基线的 2.04 降到
**1.52**，方向上与「拆掉放大器」一致，但这不足以当结论。要定量必须独占测量或搬 CI runner。

### 剩下的成本不在渲染

160 回合仍有 `longest=449ms`、`>50ms=102 of 106`，与 §十五 的 DOM 事实一致：正文已 24,035 px、7,560 节点，
成本在布局与绘制。**行渲染已不是瓶颈**，下一步若要继续就得动虚拟化/内容分块，而不是 React。

## 二十九 容器 memo 被回调身份击穿：每回合 11 次重走全表 → 3.7 次（确定性计数）

上一节把「行渲染」压到 0.17 次/提交后，配置里还剩一处更大的活：**容器自己**每回合渲染 11 次，而每次渲染都要
把整条记录走一遍（逐条建 props 依赖元组、建修订签名、查逐槽缓存）。行便宜了，容器没便宜。

### 先证明是谁击穿了 memo（探针，跑完即删）

`WorkspaceMessageScroller` 是 `memo` 的，比较器只看三件事：两个回调的身份与「记录结构是否相同」。给比较器加
临时计数后，40 回合读数：

```
[compare] {"calls":434,"send":434,"structure":157}
```

**434 次比较里 434 次是 `onSendEditedMessage` 身份不同**——它不是「偶尔变」，是每次父层渲染都换。`structure`
157 次是真实的结构变化（新消息、状态翻转），`onAnnotateImage` 0 次。也就是说：容器那 11 次/回合的渲染里，
约 7 次纯粹是回调身份churn，和记录内容毫无关系。

根因在 `WorkspacePage`：`sendEditedMessage` 的依赖里带着运行时钩子给的 `resendEditedMessage`，后者每次渲染
换身份，于是 `useCallback` 等于没上锁。

### 改法：最新引用桥（与容器里既有的 `liveActionHandlersRef` 同一套）

把实现放进 ref（每次渲染刷新、渲染期写、带 `eslint-disable react-hooks/refs` 与理由），回调本身只依赖
`activeSessionId`，调用时永远读最新实现 ⇒ 身份恒定，且**不会**出现「闭包捕获旧会话」那类问题（这正是本项目
不许「直接把回调从依赖里拿掉」的原因）。

## 三十 一半的 store 提交是空写：setBranchSwitchBlocked

行渲染降到个位数之后，下一层的成本是「提交本身」——每次提交会唤醒全部订阅者（每回合选择器被调用 794 次）、
并让容器重渲一次。于是给提交加了来源归因：store 的每个 action 在调用前后打上标签，提交记到该 action 名下
（压栈式取函数名在压缩产物里只能得到 `set2`，无用）。

40 回合首测：

```
[origins] setBranchSwitchBlocked=380 | setContextUsage=93 | appendUserMessage=40 | completeActivityGroup=40
          appendAgentMessageChunk=40 | finishRun=40 | applyDurableSessionProjection=34 | setAgentPromptInFlight=34
```

**`setBranchSwitchBlocked` 一个人占 735 次提交里的 380 次（52%）**。两处浪费：

1. 这个 setter 内部有「值没变就不改」的判断，但**仍然调用 `set(...)`**：`sessions.map` 每次返回新数组 ⇒
   新 state 对象 ⇒ 全部订阅者被唤醒。判断写在 map 内部，挡不住「分配」这一步；
2. 调用它的 effect 把「复位成 false」写进了 cleanup：编辑可用性每翻转一次，先写 `false` 再写 `true`，
   一次翻转两条提交。

修法：setter 先 `get()` 查一次，值相同直接 return；effect 的复位挪到只依赖 sessionId 的独立 effect（只在
卸载/换会话时复位）。

改后：

```
[commits] 735 → 495（每回合 18.4 → 12.4，−33%）
[origins] setBranchSwitchBlocked=380 → 186
[render-count] 行渲染仍为 120（40 回合），每次提交 0.16 → 0.24
```

行渲染没有变差（0.24 行/提交，仍 ≤1），但**每回合的提交少了三分之一**，意味着订阅者扫描与容器重渲同比减少。

### 还没解决：编辑可用性本身在抖

剩下的 186 次提交不是空写——`branchSwitchBlocked` 真的在 true/false 之间来回切，也就是 `canEditMessage`
每个回合翻转约 4.7 次。按定义它一回合只该变两次（开始跑→不可编辑、跑完→可编辑）。多出来的翻转来自它的
某个输入在流式过程中抖动（`activeSessionHasRuntimeInteraction` 最可疑），这一项还没定位，记在这里。

### 验证

- 全量 unit：**1,464 files / 18,325 passed / 227 skipped / 0 failed**；
- `e2e/workspace-conversation.spec.ts`（编辑→修订持久化→重开）：**3 passed**；
- `typecheck:web` 0；同批次 160 回合墙钟 task **205.8** / script **126.1 ms**（上一批次 226.7 / 140.4），
  方向一致但跨批次不可当结论。

## 三十一 提交计数先修正了一次口径，再定位到 isReviewing

### 计数口径：只算真正唤醒订阅者的写入

之前的 `[origins]` 计的是「`set` 被调用次数」，而不是「状态真的变了」。像 `setContextUsage` 这类 setter 在值相同时
返回**同一个 state 对象**，zustand 的 `Object.is` 判定相等后**不会通知任何订阅者**——但计数器照样 +1。
把计数改成比较前后 state 身份后，同一场景：

```
setContextUsage 99 → 6        ← 93 次是「值没变」的空调用，从来不通知
setBranchSwitchBlocked 380 → 214（修正口径后仍为真实写入，改前的空写是真新对象）
```

结论修正：§三十 里对 `setBranchSwitchBlocked` 的修复是**真的**（旧代码每次 `sessions.map` 造新数组、造新 state，
必然通知），但当时对其他 setter 的占比估计偏高；本条不改变修复本身，只纠正我读数的含义。

### 现在每回合 10.5 次真实提交，其中 46% 来自编辑可用性

```
[commits] 421（10.5/回合）
[origins] setBranchSwitchBlocked=195 | setAgentPromptInFlight=52 | setAwaitingFirstAgentOutput=52
          appendUserMessage=40 | appendAgentMessageChunk=40 | finishRun=40 | setContextUsage=2
[edit-inputs] reviewing=136 | status=80 | runtimeInteraction=52
```

编辑可用性的抖动来自 `isReviewing`（136 次/40 回合 = 3.4 次/回合）：**自动审查在每个回合开始跑一次、跑完停一次**，
于是 `canEditMessage` 随之前后翻转，每次都把 `branchSwitchBlocked` 写进 store。

**这不是缺陷，是真实生命周期**——审查确实在跑，编辑确实要禁。40 次提交里 `status` 80、`runtimeInteraction` 52
也都是同一件事的不同侧面。

### 所以这条线到这里收

要继续削，只能不动 store：把 `branchSwitchBlocked` 从 store 里拿掉、改成切换分支时现读现算。代价是把一个
「跨模块共享的守卫」变成「点击时计算」，属于架构取舍，收益是每回合少 ~5 次通知；在行渲染已经 ≤1/提交的今天，
这点收益不值得为它改共享守卫的语义。**记录在此，不实施。**

## 三十二 结案：19 倍矛盾是计量污染，不是抖动

§二十七 留了一个矛盾：行级 `edit` 变化 3,323 次，而 `WorkspaceMessageEditStateProvider` 自己的值只翻转 173 次
（同为 40 回合），差 19 倍，当时判「现有计数器无法解释」。

现在可以结案了，两个原因叠在一起，都是**计量污染**：

1. **行是被父级带动的，不是被 edit 带动的。** 容器每回合重渲 11 次、每次把所有行的 props 重新摊一遍；
   行只要重渲一次，逐输入签名就会把「上一次看到的值」刷新一遍。于是同一次真实翻转会被记到**很多行**头上，
   而 Provider 那边只记一次 —— 分母与分子根本不是同一件事。
2. **每条消息在 DOM 里有两个副本**（§二十六，164 item / 82 唯一 id），两个副本共用一个按 `message.id`
   索引的签名表，互相把对方的值刷新掉，于是相邻两次渲染之间「变化」被反复记出。

修完之后同一场景（40 回合）：行渲染 **120** 次、Provider 翻转 **187** 次 —— **行渲染次数已经少于翻转次数**，
即每次真实翻转最多让 0 行重渲（只有真正消费可用性的四个控件在 `EditAvailability` 边界内重渲）。
19 倍这个数字在新口径下不存在，也不需要解释成「抖动」。

**教训写在这里**：按「同一 id 的两次渲染之间值变了」来归因，前提是「渲染由该值驱动」。这个前提不成立时，
计数会成倍放大。下一次要归因，先证明驱动关系，再数。
